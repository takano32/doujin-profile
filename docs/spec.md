## 0. 要約

- **何を作るか**: `https://profile.xwp.jp/<名前>/` に、ユーザごとの同人サークル紹介サイト(リンク集+マンガ作品の紹介)を出す。
  持ち主が lit.link のように自分で編集でき、見た目は WordPress のテーマの仕組みで変えられる。
  最初の目標は `https://takano32.github.io/f_tsf/` と同等の内容を `/ftsf/` で出すこと。
- **設計原則は「標準優先」**: WordPress の標準の仕組みに乗る。標準から外れる要件は、独自実装で押し通すより要件のほうを曲げる(ユーザ裁定 2026-09-18)。
- **v0.2 からの転換**: 独立テンプレート+スキン+構造化メタ+独自の URL 解決、という自作寄りの設計をやめ、
  **固定ページ・ブロックエディタ・ブロックテーマ**に乗せる。プラグインの中心は「同人向けの独自ブロック」と「持ち主の権限の絞り込み」になる。
- **構成の候補は 2 つ**(§4): 案 P(単一サイト。プロフィール = 固定ページ)と案 M(Multisite。プロフィール = サイト)。**推奨は案 P**。
  「ユーザごとに別々のテーマを選ばせたい」「独自ドメインをコアの標準機能で割り当てたい」が必須なら案 M だが、
  導入先のセキュリティプラグインが Multisite 非対応など、ホスト側の代償が大きい。
- **最大のリスク**は引き続きホスティング規約(§3.3)。成人向けの画像をこのサーバに置けるかは、設計より先に方針が要る。

## 1. 要件と原則

### 1.1 要件(ユーザ裁定 2026-09-18)

| # | 要件 | 補足 |
|---|---|---|
| R1 | `https://profile.xwp.jp/<名前>/` でユーザごとのサイトを出す。`f_tsf` の内容が見られるようにする | 移植元の棚卸しは §2 |
| R2 | ユーザ管理をする。認証は、他のプラグインを参考にした一般的な設計にする。権限に注意する | 付録 A |
| R3 | lit.link のように、ユーザが自分でリンク集やマンガを編集できる | 「マンガ」の範囲は要確認(D17) |
| R4 | f_tsf と違う雰囲気にもできる。プラグイン独自の仕組みだけでなく、**WordPress のテーマそのもの**を流用できる | §9 |
| R5 | 名前は WordPress の制約をそのまま適用する。標準から外れるなら `f_tsf` は諦めて `ftsf` でよい | → 原則「標準優先」 |
| R6 | 設計の過程を Markdown に残し、随時 git コミットする。ブランチは master | [`design-log.md`](design-log.md) |

検討中(未確定): 独自ドメイン(`ftsf.example.com` で `/ftsf/` の内容を見せる)。§4 の比較観点と §11 に含めた。

### 1.2 設計原則

1. **標準優先**: URL の解決、編集画面、見た目、認証は、WordPress コアの標準機能で実現する。
   コアに無いものだけを作る(同人向けのブロック、権限の絞り込み、運営用コマンド)。
2. **最小権限**: 持ち主に渡すのは、自分のページを編集するのに要る権限だけ(§7)。
3. **リポジトリが正本**: サーバ上で直接編集しない。配備は rsync、検収は WP-CLI と curl(§12)。
4. **このサーバに置かなくても成立する**: 成人向けの画像は外部 URL でも扱える形にしておく(§3.3)。

### 1.3 スコープ

| 含む | 含まない(少なくとも当面) |
|---|---|
| プロフィールページ(リンク集・作品紹介)の編集と表示 | 販売・決済・ダウンロード配信 |
| 同人向けの独自ブロック(作品カード、サンプルビューア、リンクボタン、年齢確認) | コメント・フォロー等の SNS 機能 |
| 持ち主のアカウントと権限、招待 | 公開のセルフ登録(§7.6。やるなら別途設計) |
| 運営者向けの WP-CLI(投入・書き出し・招待・公開停止・診断) | 作品本編の配信(D17 次第) |

### 1.4 用語

| 語 | 意味 |
|---|---|
| プロフィール | `/<名前>/` で公開される 1 つのサイト。1 サークル(または 1 作家)に対応する。案 P では 1 枚の固定ページ(+子ページ) |
| 名前 | プロフィールの URL 名(`ftsf`)。WordPress のユーザ名と同じもの(R5) |
| 持ち主 | そのプロフィールを編集できるアカウント |
| 運営者 | サイト所有者 = WordPress の administrator |
| 作品 | プロフィールに載せる頒布物 1 点(タイトル・発売日・販売リンク・サンプル) |
| テーマ / スタイルバリエーション / セクションスタイル / パターン | いずれも WordPress コアの用語どおり。v0.2 の「スキン」という独自用語は廃止した |

## 3. 前提と制約

### 3.1 導入先(実測の要点)

- Xserver for WordPress、`ssh profile`。**WordPress 7.1.1・単一サイト・PHP 8.0.30・MariaDB 10.11・WP-CLI 2.8.1**。サーバに node は無い(開発機には node 24 がある)。
- コアは**メジャー含め自動更新**される。コアの公開 API だけに依存し、更新で壊れにくく書く。
- `display_errors = On`。公開ページで notice / warning を出すと画面に漏れる。
- 前段に **nginx キャッシュ**があり、消去はサーバパネルからしかできない。ログ類はユーザから読めない。
- 有効テーマは Twenty Twenty-Five(ブロックテーマ)。スタイルバリエーション 8、配色プリセット 8、フォントの組 7、**セクションスタイル 5**、パターン 98(うち「Link in bio」のページ用 3)。
- `mu-plugins/` は未作成。有効プラグインは CloudSecure WP Security のみ(ログイン URL 変更が有効)。
- WordPress ユーザは `takano32` と `ftsf` で、**どちらも administrator**。
- `wp_attachment_pages_enabled = 0`(添付ファイルの個別ページは無効)。

### 3.2 mu-plugin であることの制約

| 制約 | 対処 |
|---|---|
| `mu-plugins/` 直下の `*.php` しか自動ロードされない | ローダ `doujin-profile.php` → 本体 `doujin-profile/doujin-profile.php`(ts-library と同じ構成) |
| **有効化フックが発火しない** | ロール登録などの初期化は「バージョン付きの冪等な初期化」で行う。WP-CLI からも同じ処理を呼べるようにする。DB に書かない動的ロール(bbPress 方式)も選択肢(付録 A-2) |
| rewrite rules を足すと flush の契機が無い | **足さない**。URL はコア標準(固定ページ)に任せる(§5) |
| 管理画面から無効化できない・更新通知が無い | 意図どおり。配備は rsync(§12) |

### 3.3 ホスティング規約 ★ 先に方針が要る

[XServer for WordPress 利用規約](https://wp.xserver.ne.jp/rule/rule.php)の禁止事項(2026-09-18 に原文を確認):

- (11)「猥褻な表現を含む情報、または公衆に羞恥心を抱かせるおそれのある情報、その他公衆の射幸心を仰ぐ情報を掲載し、または他の利用者もしくは第三者に提供する行為」
- (13)「未成年者にとって有害と認められる情報の売買、譲受または掲載する行為、それらを助長する行為」
- (14)「人の死体、**裸体**、児童ポルノ、人を殺傷する現場もしくは児童虐待に相当するおそれのある画像または動画を掲載する行為」
- (22)「利用者が本サービスを利用して、本サービスに定めるサービスと同様のサービスを、有償無償を問わず第三者に提供もしくは再販売、あるいは転売する行為」
- 契約解除事由 (9)「利用者が本サービスを弊社の許可なく他の本サービスの利用者または第三者に使用させた場合」

違反時は利用停止・アカウント削除・情報の削除がありうる。

参考として、別サービスであるエックスサーバー本体の [FAQ](https://www.xserver.ne.jp/support/faq/dont_contents_stint.php) は
「同人系コンテンツの運用自体は、禁止事項に該当をいたしません」としつつ
「性行為、またはそれを連想させる画像・動画を掲載している場合は、禁止事項に該当するコンテンツであるとの判断をいたします」と述べ、
ポルノサイト等への「リンクが含まれるもの」も禁止に挙げている(XServer for WordPress に同じ運用が適用されるかは未確認)。

**doujin-profile への影響**:

1. f_tsf は成人向けサンプル画像を 54 枚同梱している。これを `uploads/` に置いて表示するのは (11)(14) に当たるおそれが高い。
2. 表紙画像は外部(DMM の CDN)へのホットリンクだが、ページに表示する以上「掲載」と見なされる余地がある。
3. FANZA / DLsite の成人向け商品ページへのリンク自体がどう扱われるかは、規約の文面からは判断できない。
4. 第三者に WordPress の「サイト」そのものを持たせる形(案 M)は、(22) の「同様のサービス」に近づく。
5. **持ち主が自分で編集できる(R3)ということは、運営者の知らないうちに規約違反の素材が載りうる**ということ。初回公開の承認(D11)と公開停止の手段(§7.8)が歯止めになる。

**解釈を決めるのは Xserver であって、この文書ではない。** 取りうる方針は D1 に挙げた。

## 4. 全体構成: 2 案の比較と推奨

要件 R3〜R5 の確定で、v0.2 の比較は前提が変わった。`f_tsf` の `_` にこだわらなくなったので Multisite の最大の障害が消え、
「WordPress のテーマそのものを流用する」ためにページをブロックとして描画する(v0.2 §9.6 の段階 2 以上)ことが前提になった。

### 4.1 候補

- **案 P(Pages)**: 単一サイトのまま。プロフィール = トップレベルの**固定ページ**。`/<名前>/` はコアが標準で解決する。見た目は有効なブロックテーマ+ページごとのセクションスタイル。
- **案 M(Multisite)**: サブディレクトリ型 Multisite。プロフィール = **サイト**。`/<名前>/` はコアが標準で解決する。見た目はサイトごとにテーマを選ぶ。

どちらも URL の解決・編集画面(ブロックエディタ)・認証はコア標準で、独自ブロックは共通に使える。

### 4.2 比較

| 観点 | **案 P: 固定ページ** | 案 M: Multisite |
|---|---|---|
| `/<名前>/` の URL | ○ コア標準(固定ページ)。`f_tsf` のような `_` 入りも可 | ○ コア標準。名前は英小文字と数字(管理画面からなら `-` も)。`ftsf` は可、`f_tsf` は不可 |
| WordPress テーマの流用(R4) | △→○ 有効な**ブロックテーマ 1 つ**が全プロフィールに効く。プロフィールごとの違いはセクションスタイル(配色・文字)とパターン(レイアウト)で出す | ◎ サイトごとに、運営者が有効化したテーマの中から選べる。サイトエディタでテンプレートやフォントまで触れる |
| lit.link 風の編集(R3) | ○ ブロックエディタ。ログイン後に自分のページのエディタへ直行させ、使えるブロックを絞る | ○ 同じ。ただしサイト管理者には投稿・固定ページ・メニュー等も見えるので、絞り込みの範囲が広い |
| 認証・権限(R2) | ○ `wp_users`+専用ロール(固定ページの「自分のものだけ編集」はコア標準の権限で表現できる) | ○ `wp_users` をネットワークで共有し、権限はサイト単位。標準の考え方 |
| 内容の分離 | △ 同じテーブル・同じメディアライブラリに同居(表示上の絞り込みで対処) | ○ サイトごとに別テーブル、アップロード先も別ディレクトリ |
| 独自ドメイン(検討中) | △ コアに機能なし。mu-plugin でホスト名とページの対応を持つ(§11)。先行プラグインはある | ○ コア標準(サイトのドメインを書き換えるだけ)。ホスト側のドメイン追加はどちらの案でも要る |
| **導入先との相性** | ○ 単一サイトのまま。CloudSecure・ステージング・バックアップなどホストの道具立てがそのまま使える | **×→△ CloudSecure が Multisite 非対応**(§3.4)なので、ログイン URL 変更・試行制限などを別手段で組み直す。ホストの公式サポート可否は不明。ステージング同期やサイト URL 変更などパネルの機能が Multisite を想定しているかも不明 |
| 規約 (22) との距離 | ○ ページを載せるサービス | △ 第三者に WordPress サイトを提供する形 |
| 運用の重さ | ○ DB は標準 12 テーブル | △ サイトごとに約 10 テーブル増。ネットワーク管理が加わる。後戻りしにくい |
| 運営者の監督(§3.3) | ○ 持ち主が触れるのは 1 ページと許可したブロックだけ | △ 持ち主が投稿や固定ページを自由に増やせる(絞らなければ) |
| 自作する量 | 中: 独自ブロック、権限の絞り込み、直行 UI、セクションスタイルとパターン、WP-CLI | 中: 独自ブロック、サイト管理者の権限の絞り込み、サイト作成の自動化、セキュリティの組み直し、WP-CLI |

不採用にしたもの: v0.2 の案 A(カスタム投稿タイプ+`request` フィルタでの独自 URL 解決。付録 A-10 のとおり慢性的に壊れやすい領域で、固定ページなら同じことがコア標準でできる)、
独自ユーザ管理(v0.2 の案 C)、プロフィールごとにテーマを丸ごと切り替える方式(v0.2 §9.6 の段階 3)。

### 4.3 推奨: 案 P

- 要件 R1〜R5 をすべて**コア標準の仕組みだけ**で満たせ、導入先の道具立て(CloudSecure、ステージング、バックアップ、サポート)も失わない。
- 案 M が優れるのは「ユーザごとに別々のテーマ」と「コア標準の独自ドメイン」の 2 点。どちらも今の時点では必須要件ではない。
- 内容はどちらの案でも標準のブロックマークアップなので、**案 P で始めて、あとから案 M へ移す**ことはできる(ページの内容をサイトへ移すだけ)。逆(M → P)も可能だが、Multisite 化そのものの後戻りが重い。
- 案 M を選ぶ場合は、先に 👤 Xserver へ Multisite の可否を確認し、ステージング環境で「Multisite 化 → CloudSecure 無効化 → `/ftsf/` サイト作成 → パネル機能(同期・バックアップ)の動作」を試す。

### 4.4 段階導入

| 段階 | ログインする人 | できること |
|---|---|---|
| Phase 1 | 運営者だけ | 独自ブロックとテンプレートで `/ftsf/` を f_tsf 相当に表示。内容は運営者がブロックエディタと WP-CLI で入れる |
| Phase 2 | 招待された持ち主 | 自分のページだけをブロックエディタで編集(lit.link 風の導線) |
| Phase 3 | (要検討) | 独自ドメイン、セクションスタイルの追加取り込み、公開登録の是非 |

以下 §5〜§9 は案 P を前提に書く。案 M で変わる点は各節の末尾に「案 M では」として添える。

## 5. URL と名前

### 5.1 URL(すべてコア標準の固定ページ)

| URL | 実体 |
|---|---|
| `/<名前>/` | トップレベルの固定ページ(slug = 名前、作成者 = 持ち主) |
| `/<名前>/<子>/` | その子ページ(例 `/ftsf/announce/`)。要るものだけ運営者が作る |

rewrite rules の追加も、`request` フィルタでの介入もしない。末尾スラッシュや大文字の正規化、非公開ページの 404 もコアの挙動のまま。

### 5.2 名前 = WordPress のユーザ名(R5)

- プロフィールの名前は、持ち主の WordPress ユーザ名(`user_login`)と同じにする。ページの slug もそれと同じ。
  運用上の条件は 1 つだけ: **ユーザ名がそのまま slug になること**(`sanitize_title( ユーザ名 ) === ユーザ名`。つまり英小文字・数字・`_`・`-`)。招待コマンドが検査する。
- **ユーザ名は公開情報になる**。これは WordPress コアの立場(「ユーザ名は秘密ではない」付録 A-6)と同じで、X や GitHub と同じ考え方。
  v0.2 の「ログイン名を URL に晒さない」方針はここで取り下げる。代わりに、防御の本体をパスワードの強度・試行制限・2 段階認証に置く(§10)。
- 最初のプロフィールは `/ftsf/`(既存ユーザ `ftsf`)。
- 名前の変更は運営者だけ。旧 URL からの転送はコア標準の旧 slug リダイレクトに任せる(固定ページで効くかは未検証)。

### 5.3 衝突の防ぎ方

- トップレベルの固定ページを作れるのは運営者だけ(§7.3)。持ち主は自分のページの slug・親・作成者・テンプレートを変えられない。
- 招待コマンドは、その名前が既存の固定ページ・添付ファイルの slug・コアの経路(`wp-admin` `wp-json` `feed` `author` `page` `embed` など)・
  運営用に取っておく語(`login` `admin` `about` `terms` `privacy` `contact` など)と衝突しないことを検査する。
- **落とし穴**: コアは固定ページと添付ファイルの slug を同じ名前空間で一意化する。メディアライブラリに直接 `hoge.jpg` を上げると添付ファイルの slug `hoge` が先に取られ、あとから作る固定ページが `hoge-2` になる。
  持ち主のアップロードには slug に接尾辞を付けて、将来の名前を先取りさせない。

案 M では: 名前 = サイトのパス。規則と予約語はコアが持つ(英小文字と数字、予約 10 語+禁止ユーザ名 7 語。付録 A-10)。

## 6. コンテンツ: ブロックで持つ

### 6.1 プロフィールページの構成

```
固定ページ(slug = 名前、テンプレート = 「プロフィール」)
└─ グループ(全幅・全高。ここに付けるセクションスタイルが、このプロフィールの配色と文字を決める)
   ├─ プロフィールヘッダ    … 独自ブロック: アイコン・名称・リード文・ページ内ナビ
   ├─ 作品一覧              … 独自ブロック: 中の作品カードを 最新作 / 新作予告 / これまでの作品 に自動で振り分け
   │   └─ 作品カード × n    … 独自ブロック
   ├─ リンクボタン(販売ページ)… 独自ブロック
   ├─ リンクボタン(アカウント)… 独自ブロック
   └─ (見出し・段落・画像・スペーサーなど、許可したコアのブロック)
```

- 「プロフィール」テンプレートはプラグインが登録する(`register_block_template()`。実測で利用可)。サイト共通のヘッダ・フッタ(サイト名「プロファイル」やナビ)を出さない白紙のテンプレート。
- 内容はすべて `post_content`(標準のブロックマークアップ)に入る。変更履歴はコア標準のリビジョンで残る。
- ページ単位の設定(成人向けフラグなど)は登録済みの投稿メタで持ち、エディタのサイドバーから切り替える。

### 6.2 独自ブロック

| ブロック | 属性(主なもの) | 表示側の挙動 |
|---|---|---|
| プロフィールヘッダ | アイコン(メディア)、名称 (ja, en)、リード文 (ja, en)、ナビの有無 | ページ内のセクションからナビを自動生成 |
| 作品一覧 | 見出しの文言 (ja, en) | 子の作品カードを発売日時で 3 区分に振り分けて描画。予告が無ければ「新作予告」を出さない |
| 作品カード | タイトル・あらすじ (ja, en)、発売日時、発売日の表記(発売前・発売後、各 ja, en)、表紙(メディア / 外部 URL / FANZA ID)、販売リンク[](サービス種別・URL・sponsored・発売前の URL)、サンプル画像[](メディア / 外部 URL) | サンプルビューア(前後移動・矢印キー・Esc・枚数表示)。発売前後でリンクと表記を差し替え |
| リンクボタン | リンク[]: サービス種別(FANZA・DLsite・メロンブックス・とらのあな・BOOTH・pixiv・X・note・Circle.ms・Bluesky・Misskey・Fantia・FANBOX・Skeb・YouTube・その他)、URL、表示名 (ja, en)、sponsored | `rel` を自動で付ける(`noopener`、sponsored なら `sponsored`)。アフィリエイト表記の要否を判定 |

- どれも**サーバ側で描画する動的ブロック**にする(保存されるのは属性だけ)。表示の修正を、保存済みの全ページに後から効かせられる。
- 見た目はテーマに委ねる: 色・文字・余白はテーマのプリセット(CSS 変数)を参照し、ボタンはテーマのボタン要素のスタイルを継ぐ。独自ブロックにもコアの色・文字・余白の設定欄を付ける。
  こうしておけば、テーマやセクションスタイルを替えたときに独自ブロックも一緒に雰囲気が変わる(R4)。
- 表示側の JavaScript は、コア標準の Interactivity API を第一候補にする。
- エディタ用の JavaScript はビルドが要る。開発機(node 24)でビルドし、成果物をリポジトリに入れて配備する(サーバに node は無い)。

入力値の規則: URL は `https:` のみ。テキストはプレーンテキスト。メディアは持ち主本人がアップロードした画像だけ。件数に上限(作品 200、リンク 30、サンプル 80 枚/作品 など。値は実装時に確定)。
検証はサーバ側の描画時と保存時(REST)の両方で行う。

### 6.3 持ち主が使えるブロック

持ち主には、独自ブロックと、害の少ないコアのブロック(見出し・段落・リスト・画像・ギャラリー・スペーサー・区切り・グループ・カラム・ボタン)だけを見せる(`allowed_block_types_all`)。
カスタム HTML・ショートコード・クエリループ・サイト系のブロックは出さない。外部の埋め込み(YouTube や X)を許すかは D18。
`unfiltered_html` は与えないので、どの経路でもスクリプトは保存時にコアが除去する。

### 6.4 パターン

- プラグインが「同人サークルのリンク集(f_tsf 風)」のスターターパターンを登録する。新しいプロフィールはこのパターンから始める。
- 有効テーマのパターンはそのまま使える(TT5 の「Link in bio」3 種など)。

## 7. 認証・権限

### 7.1 方針

1. **アカウントは WordPress のユーザ**(付録 A-1)。独自のユーザテーブル・独自認証は作らない。
   パスワードの保管、認証 Cookie、nonce、パスワードリセット、CloudSecure の防御(ログイン URL 変更・試行制限・2 段階認証・画像認証)をそのまま使う。
2. **名前 = ユーザ名 = ページの slug**(§5.2)。持ち主とページの対応は、固定ページの作成者(`post_author`)。
3. **持ち主に渡すのは専用ロールだけ**。administrator / editor を流用しない。
4. **登録は閉じたまま**(`users_can_register = 0` を維持)。アカウントは運営者が作る(招待制)。
5. **管理者は運営者だけ**にする(§7.7)。

### 7.2 なぜ administrator を渡してはいけないか(実測に基づく)

`DISALLOW_FILE_EDIT` が未設定なので、administrator は管理画面からテーマ/プラグインの PHP を編集できる。
つまり **administrator = このホスティングアカウント上で任意のコードを実行できる権限**であり、全プロフィール・全ユーザ・DB に及ぶ。

### 7.3 専用ロール `doujin_member`

固定ページの「自分のものだけ編集できる」は、コア標準の権限の組み合わせで表現できる(実測: コア既定の author は固定ページの権限を持たず、editor は他人のページも編集できる。ちょうどよいロールが無いので作る)。

| 権限 | 持ち主 | 理由 |
|---|---|---|
| `read` | ○ | 管理画面に入るための最小権限 |
| `edit_pages` / `edit_published_pages` | ○ | 自分の固定ページの編集(公開後も) |
| `edit_others_pages` / `edit_private_pages` / `delete_*_pages` | × | 他人のページに触れない。削除は運営者だけ(名前の使い回し・乗っ取り防止) |
| `publish_pages` | **×**(D11) | 初回公開は運営者が承認する。規約リスク(§3.3)の歯止め。公開後の編集は `edit_published_pages` で即時反映される |
| 固定ページの新規作成 | **×** | コア既定では `edit_pages` があれば何枚でも作れてしまう。`page` の `create_posts` を別の権限に対応付け(`register_post_type_args` フィルタ)、運営者だけに与える |
| `upload_files` | ○(画像のみ) | アイコン・OGP・サンプル用。下の制限とセット |
| `edit_posts` ほか投稿系・`unfiltered_html`・`edit_theme_options`・`manage_options` など | × | — |

コア標準だけでは足りず、プラグインが補うもの(いずれも小さなフィルタ):

- 持ち主による slug・親ページ・作成者・テンプレートの変更を保存時に無効化する。
- メディアライブラリは自分のアップロードだけが見えるようにする(一覧・モーダル・REST の 3 経路)。受け付けるのは画像だけ。1 枚のサイズとユーザあたりの総量に上限。
- 添付ファイルの編集・削除権限はコアでは「投稿」の権限に紐づくため、`upload_files` だけでは自分の画像を消せない。ここだけ権限の対応付けを補う。
- **アップロードした画像は、その時点で公開物として扱う**(`uploads/` は直接配信され、コアは未認証でもメディア一覧を返す。付録 A-4)。「未公開にしたい素材はアップロードしない」と持ち主に明示する。

ロールの登録は §3.2 のとおり。既存ロールに対する `add_role()` の再実行は何もしないので、権限の増減は差分を `add_cap()` / `remove_cap()` で適用する(付録 A-5)。

### 7.4 メディアと `uploads/`

`uploads/` では PHP が実行されない(実測: Xserver の拒否ブロックあり)。画像の縮小は GD(実測: WebP 可・AVIF 不可・imagick なし)。

### 7.5 ログイン後の導線(lit.link 風にする要)

- ログインはコアのログイン画面(CloudSecure が URL を変更済み)。持ち主には URL を個別に伝える。
- **ログインしたら、自分のページのブロックエディタへ直行**させる(ダッシュボードを経由しない)。エディタは既定で全画面表示なので、管理画面のメニューは視界に入らない。
- 管理メニューは「自分のページ」「メディア(自分の分)」「アカウント(パスワード変更)」だけにする。ツールバーの不要項目も消す。
- 公開ページを見ている持ち主には「このページを編集」への導線を出す(コア標準のツールバー)。
- Application Passwords は持ち主には無効化する(権限の絞り込みができず、全権限を引き継ぐため。付録 A-8)。

### 7.6 招待の流れ

1. 運営者が `wp doujin invite <メール> --name=<名前>` を実行(名前の検査は §5.3)。
2. ユーザを `doujin_member` で作成し、その人を作成者とする下書きの固定ページ(テンプレート = プロフィール、内容 = スターターパターン)を作る。
3. コア標準の通知メールが、パスワード設定用のリンク(期限 24 時間のリセットキー)を送る(付録 A-7)。
4. 持ち主が内容を編集して「レビュー待ち」にする → 運営者が確認して公開。

公開のセルフ登録は含めない。やる場合はメール確認・ボット対策・承認キュー・利用規約への同意・名前の占拠対策が一式必要で、規約 (22)(§3.3)との関係も先に確認が要る。

### 7.7 既存アカウント `ftsf` の扱い 👤

Phase 2 の時点で `ftsf` を administrator から `doujin_member` に変更し、`/ftsf/` の作成者にする(D6)。
あわせて `wp-config.php` に `DISALLOW_FILE_EDIT` を入れることを推奨。

### 7.8 公開停止と退会

- 運営者は `wp doujin unpublish <名前> --reason=…` で即時に非公開化できる(理由と日時を記録)。
- アカウント停止はロールの剥奪+セッション破棄。ページと名前は保持する(再取得・なりすまし防止)。

案 M では: 持ち主は自分のサイトのユーザになる。サイト管理者の既定の権限は広い(投稿・固定ページ・メニュー・テーマ切替・サイトエディタ)ので、どこまで絞るかを別途決める。Multisite では `unfiltered_html` はスーパー管理者以外に与えられない(コアの仕様)。

## 8. 編集体験(lit.link のように)

### 8.1 ブロックエディタを編集画面にする

lit.link の編集は「部品を足す・並べ替える・その場で書き換える・すぐ見た目が分かる」。WordPress でこれに当たる標準の道具がブロックエディタで、
ブロックテーマではエディタの中の見た目が公開ページとほぼ一致する。独自の編集画面を作らずに R3 を満たせる。

lit.link に寄せるための工夫(どれも小さい):

| 工夫 | 内容 |
|---|---|
| 直行 | ログインしたら自分のページのエディタが開く(§7.5) |
| 部品を絞る | 挿入できるブロックを独自ブロック+少数のコアブロックに限る(§6.3)。迷わせない |
| 雛形から始める | 新しいプロフィールはスターターパターン入りで作る(§6.4) |
| 雰囲気を選ぶ | いちばん外のグループを選ぶと、スタイル欄に配色の候補が並ぶ(§9.2。コア標準の UI) |
| スマホ | ブロックエディタはスマホでも動くが、lit.link ほど軽快ではない。ここは妥協点として明記しておく |

それでも足りない場合(スマホでの編集が主になる、など)は、Phase 3 で専用のフロントエンド編集画面を検討する。会員系プラグインの主流はフロント完結だが(付録 A-9)、編集 UI の自作は実装量と不具合の余地が大きい。

### 8.2 運営者の道具(WP-CLI)

| コマンド | 内容 |
|---|---|
| `wp doujin invite <メール> --name=<名前>` | §7.6 |
| `wp doujin import <json> [--dry-run]` / `export <名前>` | JSON とブロックの相互変換(§6.5)。名前をキーに冪等 |
| `wp doujin list` | プロフィールの一覧(名前・持ち主・状態・最終更新) |
| `wp doujin unpublish <名前> --reason=…` | 公開停止(§7.8) |
| `wp doujin doctor` | 環境・ロール・堅牢化の自己診断(読み取り専用) |

## 9. 見た目: WordPress のテーマを流用する(R4)

### 9.1 テーマはそのまま効く

プロフィールページは有効なブロックテーマ(いまは Twenty Twenty-Five)で描画される。テーマの文字・色・ボタン・余白の設計が独自ブロックにも及ぶ(§6.2)。
運営者がサイトのテーマやスタイルバリエーションを替えれば、全プロフィールの基調が替わる。ブロックテーマなら wordpress.org のどれでも使える。

### 9.2 プロフィールごとの雰囲気: セクションスタイル

WordPress 6.6 以降の標準機能で、グループなどのブロックに「配色と文字のひとまとまり」を当てられる。TT5 は 5 種を同梱している(実測)。
プロフィールのいちばん外のグループにこれを当てると、そのプロフィールだけ別の雰囲気になる。

- プラグインから追加登録できる(`register_block_style()` に theme.json 形式のスタイルを渡す。実測でコアが対応)。最初に足すもの:
  f_tsf の紫×白、f_tsf の過去 4 種(PROOF SHEET / BOUDOIR NOIR / LACQUERED PLUM BOUDOIR / HOT-PINK PULP)の配色。
- **他のブロックテーマのスタイルバリエーションも、セクションスタイルに変換して取り込める**(`styles/*.json` は同じ theme.json 形式)。
  サーバに入っている既定テーマだけでバリエーションが 28 個ある(実測)。変換は WP-CLI で行い、結果をリポジトリに入れる(Phase 3)。
- 取り込み時に文字と背景のコントラスト比(WCAG AA)を検査する。

### 9.3 レイアウト: パターン

テーマのパターンがそのまま使える(TT5 に 98 個。「Link in bio」のページ用 3 種を含む)。プラグインのスターターパターン(§6.4)もここに並ぶ。

### 9.4 フォント

コア標準のフォントライブラリ(6.5 以降)を使う。運営者が管理画面からフォントを入れると、**WordPress がファイルをダウンロードして自サイトから配信する**ので、閲覧者のブラウザが外部のフォント配信へ通信しない。
日本語フォントはファイルが大きい(1 書体あたり数 MB)点に注意(D15)。

### 9.5 この案でできないこと

ユーザごとに**別々のテーマ**を選ぶこと。単一サイトで有効にできるテーマは 1 つ。これが必須なら案 M(§4)。

### 9.6 head・年齢確認・時刻で変わる表示

- head: title はコア、説明文は固定ページの抜粋、OGP 画像はアイキャッチ画像。OGP / Twitter Card / JSON-LD / canonical はプラグインがプロフィールページにだけ出す。
  成人向けのページには `<meta name="rating" content="adult">`。
- 年齢確認: 成人向けフラグがオンのページにだけ出す。確認結果は localStorage。「いいえ」で本文を消して離脱。ダイアログとしてのフォーカス管理を足す。
- 時刻で変わる表示: サーバ側は描画時点の状態で HTML を作る。前段 nginx キャッシュはこちらから消せない(実測)ので、発売日時を埋め込み、
  **クライアント側でも現在時刻で振り分けとリンク差し替えを行う**。キャッシュが古くても発売時刻ぴったりに切り替わる。
- 未検証: 前段キャッシュの寿命と、ログイン中の持ち主に対する振る舞い(編集直後に古いページが見えるか)。Phase 0 で実測する。
- `display_errors = On`(実測)なので、動的ブロックの描画は未定義キーや型のゆらぎで notice を出さないよう、値を正規化してから出力する。

案 M では: サイトごとにテーマ・スタイルバリエーション・フォントを選べる。持ち主にサイトエディタを開くかどうかを決める必要がある。

## 11. 独自ドメイン(検討中・未確定)

`ftsf.example.com` で `/ftsf/` の内容を見せたい、という案。f_tsf には元ドメイン `ftsf.me` があり(稼働中)、canonical の向き先(D8)とも地続き。

- **ホスト側**(§3.4): パネルでドメインを追加すると無料 SSL も付く。追加時に自動で入る「プライマリドメインへの 301」はパネルで変更できる。
  301 を外したとき、そのドメインで同じ WordPress が応答するかはマニュアルに記載が無い(**未検証**。ステージングでは独自ドメインを使えないとあるので、本番での確認になる)。
- **案 P**: コアに機能が無いので、mu-plugin が「ホスト名 → ページ」の対応表を持ち、そのホスト名で来たリクエストではトップ `/` をそのページに解決し、生成する URL と canonical をそのドメインに合わせる。
  単一サイトでの先行プラグインはあるが、標準優先の原則からは外れる。
- **案 M**: コア標準(4.5 以降、サイトのドメインを書き換えるだけ)。
- どちらの案でも、ログインと編集はプライマリドメイン(`profile.xwp.jp`)で行う。

独自ドメインが必須要件なら、§4 の比較は案 M に傾く。まず要件かどうかを決める(D8)。

## 付録 A. 参考にする既存プラグインとコアの仕組み

2026-09-18 に Web で調査した結果(公式ドキュメント・公式リポジトリを優先。調査は別エージェントが行い、出典を付けて報告したもの)。
番号は本文からの参照用。「推測」と書いたものは事実ではなく調査からの見立て。

### A-1. アカウントの置き場所 — ほぼ全員が `wp_users`

- BuddyPress・bbPress・Ultimate Member・WooCommerce・MemberPress はいずれも `wp_users` / `wp_usermeta` が唯一のアカウント基盤で、独自テーブルは `user_id` を持つ付属データ。
  bbPress は独自テーブルを作らない([bbPress](https://codex.bbpress.org/getting-started/before-installing/stored-database-data/))。
  MemberPress は「ユーザの作成・保存・管理・認証を完全に WordPress API に依存」と明記([MemberPress](https://memberpress.com/docs/where-is-data-stored/))。
- 独自のユーザテーブル+独自認証は少数派(Simple Membership、WP eMember)。しかも Simple Membership の公式文書自身が「会員レコードと WP ユーザレコードの 2 つを作って連携する」と述べており、
  結局は二重管理になっている([Simple Membership](https://simple-membership-plugin.com/understanding-the-connection-between-simple-membership-members-and-wordpress-users/))。
- 「アカウントを持たない人」を扱う定石は独自認証ではなく、`user_id` を空にできるデータ側の設計(WooCommerce、Easy Digital Downloads の customers テーブル)。
  → 本仕様の「プロフィールは投稿、持ち主は任意で紐付く」と同じ考え方。

### A-2. 低権限ロール

- WooCommerce の `customer` ロールの権限は `read` だけ([class-wc-install.php](https://github.com/woocommerce/woocommerce/blob/trunk/plugins/woocommerce/includes/class-wc-install.php))。
- 管理画面からの締め出しはロール名ではなく**権限で判定**: `edit_posts` / `manage_woocommerce` / `view_admin_dashboard` のどれも無ければ My Account へ転送。
  `admin-ajax.php` と `admin-post.php` は除外([class-wc-admin.php](https://github.com/woocommerce/woocommerce/blob/trunk/plugins/woocommerce/includes/admin/class-wc-admin.php))。いちばん真似しやすい形。
- Ultimate Member はロールごとに「wp-admin に入れるか」「管理バーを隠すか」を設定で持つ([UM](https://docs.ultimatemember.com/article/103-user-roles-settings))。
- bbPress の動的ロール: ロールを DB に保存せず実行時に `$wp_roles` へ足す。理由は「ロールや権限を変えるたびに DB 移行スクリプトが要るのは労力に見合わない」
  ([bbPress フォーラム](https://bbpress.org/forums/topic/roles-and-capabilities-in-bbpress-2-2/))。有効化フックの無い mu-plugin と相性がよい。

### A-3. 公開される人物像とアカウントの分離

- Co-Authors Plus: guest author は投稿タイプ `guest-author`。公開 slug は専用メタ、WP ユーザとの連携は `cap-linked_account`
  ([ソース](https://github.com/Automattic/Co-Authors-Plus/blob/master/php/class-coauthors-guest-authors.php))。
- PublishPress Authors: 著者の実体はタクソノミーのターム。WP ユーザとの対応は term meta で、無ければゲスト = アカウント不要
  ([ソース](https://github.com/publishpress/PublishPress-Authors/blob/development/src/core/Classes/Objects/Author.php))。
- コア: 著者 URL の slug は `user_nicename`(varchar 50)。`user_login` と別の値にできる。予約ユーザ名は `illegal_user_logins` フィルタ。
- BuddyPress のプロフィール URL は既定で `user_nicename`。Ultimate Member は 7 種類から選べる(ユーザ名・氏名・ID・ハッシュ・任意のメタ)。
- **Ultimate Member は、プロフィール URL から `/user/` を取り除いてルート直下にすることを公式に「不可能」としている**。理由はコアの予約語と経路の競合
  ([UM](https://docs.ultimatemember.com/article/1890-remove-the-word-user-or-profile-from-the-profile-url))。→ v0.2 の独自 URL 解決をやめた理由(§4.2)。

### A-4. 「自分の投稿だけ編集可」の標準手法

- `capability_type` が `post` / `page` 以外だと `map_meta_cap` は既定で false。**明示的に true にする**([WP_Post_Type::set_props](https://developer.wordpress.org/reference/classes/wp_post_type/set_props/))。
- 所有者限定は「`edit_others_*` / `delete_others_*` を与えない」ことで実現する。公開済みの自分の投稿の編集には `edit_published_*` が要る([map_meta_cap](https://developer.wordpress.org/reference/functions/map_meta_cap/))。
- `create_posts` は既定で `edit_posts` 相当に対応付けられる([get_post_type_capabilities](https://developer.wordpress.org/reference/functions/get_post_type_capabilities/))。→ §7.3 で別権限に分けた理由。
- メディア: コアは既定で絞り込まない。絞るなら `ajax_query_attachments_args`(モーダル)・`pre_get_posts`(一覧)・`rest_attachment_query`(REST)の 3 経路。
  ただし表示上のフィルタであってアクセス制御ではなく、`/wp-json/wp/v2/media` は未認証で全件一覧できる。→ §7.3・§10。
- `unfiltered_html` を与えると KSES フィルタが丸ごと外れる = 保存型 XSS に直結。低権限ロールには付けない。

### A-5. mu-plugin の制約

- 「must-use プラグインでは有効化フックは実行されない」「サブディレクトリは探さない」([公式](https://developer.wordpress.org/advanced-administration/plugins/mu-plugins/))。
- `add_role()` はオプションに書き込む。毎回呼ばず条件付きで。**既存ロールへの再実行は権限リストの変更も含めて何もしない**([add_role](https://developer.wordpress.org/reference/functions/add_role/))。
- `flush_rewrite_rules()` は「性能面で極めて高コスト」([公式](https://developer.wordpress.org/reference/classes/wp_rewrite/flush_rules/))。→ rewrite rules を足さない(§3.2・§5.1)根拠。
- 「バージョン付きの初期化」を明文で推奨する公式文書は見つかっていない(上の注意書きからの実務的な帰結 = 推測)。

### A-6. ユーザ列挙

- コアの公式見解: 「ユーザ名やユーザ ID は秘密と見なさない。REST の `/wp/v2/users` が公開で見えるのは意図したもの」
  ([Reporting Security Vulnerabilities](https://make.wordpress.org/core/handbook/testing/reporting-security-vulnerabilities/))。
- 経路は 4 つで条件が違う: `/?author=N`(公開投稿があるとき転送)、REST(`show_in_rest` な投稿タイプで公開投稿を持つユーザ。`public` かどうかは関係ない)、
  ユーザサイトマップ(`public` な投稿タイプで公開投稿を持つユーザ)、**oEmbed**(`author_name` と `author_url` を返す。見落とされやすい)。
- 未認証で返るのは `slug`(`user_nicename`)と `name`(`display_name`)だけ。`user_login` とメールは返らない。→ §10 の安価な緩和。
- 止め方: `rest_endpoints`、`wp_sitemaps_add_provider`([告知記事](https://make.wordpress.org/core/2020/07/22/new-xml-sitemaps-functionality-in-wordpress-5-5/))、`oembed_response_data`。

### A-7. 登録の流れ

- `wp_new_user_notification()` は平文パスワードを送らず、パスワード設定リンクを送る。鍵はハッシュして保存され、期限は既定 24 時間
  ([get_password_reset_key](https://developer.wordpress.org/reference/functions/get_password_reset_key/))。→ §7.6 の招待はこれに乗る。
- 招待制そのものはコアに無い。実質は「登録を閉じる+管理者が作る」。
- WordPress 7.0 で、一般設定の「新規ユーザのデフォルト権限」から Administrator と Editor が外された
  ([7.0 Field Guide](https://make.wordpress.org/core/2026/05/14/wordpress-7-0-field-guide/))。背景に、登録フォームの既定ロールを管理者にできてしまう権限昇格の実例がある。
- オープン登録のスパム被害は実例多数。BuddyPress は単一サイトでも `signups` テーブルでメール確認の 2 段階。

### A-8. コアの認証まわり

- WordPress 6.8 でパスワードは bcrypt に。リセット鍵や Application Passwords は BLAKE2b。既存ハッシュは次回ログイン時に自動で更新
  ([告知](https://make.wordpress.org/core/2025/02/17/wordpress-6-8-will-use-bcrypt-for-password-hashing/))。
- Application Passwords は REST / XML-RPC の Basic 認証専用で、**権限の絞り込みができず、そのユーザの全権限を引き継ぐ**
  ([統合ガイド](https://make.wordpress.org/core/2020/11/05/application-passwords-integration-guide/))。→ §7.5 で持ち主には無効化する理由。
- 2 段階認証は 2026-09 時点でもコアに無く、プラグイン([Two-Factor](https://wordpress.org/plugins/two-factor/))。
- nonce は認証・認可の代わりにならない。必ず `current_user_can()` と組み合わせる([Nonces](https://developer.wordpress.org/apis/security/nonces/))。

### A-9. フロントエンド編集か、管理画面か

- 会員系プラグインは**フロントで完結させるのが主流**(WooCommerce の My Account、MemberPress と Paid Memberships Pro の「会員をダッシュボードに入れない」設定、Ultimate Member)。
- 一方で「低権限ユーザに wp-admin を見せるべきでない」という WordPress 公式の推奨は見つかっていない。コアの既定はむしろ、`read` 権限でダッシュボードと自分のプロフィールに入れる。
- 公式が求めるのは場所を問わず nonce + 権限検査 + サニタイズ/エスケープの 3 点([Security](https://developer.wordpress.org/apis/security/))。
- 推測: フロント編集の利点は攻撃面の縮小と使い勝手、欠点は編集 UI を全部自作することによる不具合の増加。

### A-10. ルート直下 `/<slug>/` を投稿タイプに割り当てる

- `'rewrite' => ['slug' => '']` は効かない。コアが空の slug を投稿タイプ名で上書きする([class-wp-post-type.php](https://github.com/WordPress/wordpress-develop/blob/trunk/src/wp-includes/class-wp-post-type.php))。
- 投稿タイプの rewrite rule は固定ページに構造上負ける。同名の固定ページが実在すれば必ず固定ページが勝つ。
- **`wp_unique_post_slug()` は投稿タイプをまたいで重複を防がない**([リファレンス](https://developer.wordpress.org/reference/functions/wp_unique_post_slug/))。横断の一意性は自前で担保する。
- 定石は `request` フィルタで 404 を拾い直す方式。wordpress.org 配布の [`remove-cpt-base`](https://plugins.svn.wordpress.org/remove-cpt-base/trunk/remove-cpt-base.php) がこれで、解決順は 投稿 → 固定ページ → 対象 CPT。
  更新履歴は 404 関連の修正の繰り返し = 慢性的に壊れやすい領域。
- Multisite サブディレクトリ型の予約サイト名は 10 個(`page` `comments` `blog` `files` `feed` `wp-admin` `wp-content` `wp-includes` `wp-json` `embed`)。
  ユーザ名側の禁止語は `www` `web` `root` `admin` `main` `invite` `administrator`。サイト名に使える文字は §4.2 のとおり。ユーザテーブルはネットワーク全体で共有。

### A-11. 調査で確認できなかったこと

- core.trac.wordpress.org と wordpress.stackexchange.com は本文を取得できず、チケットや回答の中身は未確認。
- 2 段階認証のコア統合の計画。Xserver for WordPress における Multisite の公式サポート可否。

## 付録 B. v0.2 からの転換点

| v0.2 | v0.3 | 理由 |
|---|---|---|
| プロフィール = カスタム投稿タイプ。`request` フィルタで `/<slug>/` を独自に解決 | プロフィール = 固定ページ。URL はコア標準 | 標準優先(J4)。独自解決は慢性的に壊れやすい領域(付録 A-10) |
| slug はログイン名と別に持ち、独自の規則(3〜32 文字、`_` と `-` の同一視など) | 名前 = ユーザ名。WordPress の制約のまま | J4 |
| ログイン名を URL に晒さない | ユーザ名は公開情報。防御の本体は試行制限と 2 段階認証 | J4。コアの立場と同じ(付録 A-6) |
| 内容 = 構造化メタ(JSON スキーマ)。編集は PHP のフォーム | 内容 = ブロック。編集はブロックエディタ | J2・J3 |
| テーマに依存しない独立テンプレート+「スキン」(トークン+同梱 CSS) | 有効なブロックテーマで描画。雰囲気はセクションスタイル、レイアウトはパターン、フォントはフォントライブラリ | J3。「スキン」という独自用語は廃止し、WordPress の用語に統一 |
| テーマからは、取り込み時にトークンだけを独自形式へ変換 | 他テーマのスタイルバリエーションを、同じ theme.json 形式のままセクションスタイルとして取り込む | 同上 |
| Multisite は `f_tsf` が作れないので不採用 | `ftsf` でよくなったので再評価(案 M)。ただし CloudSecure が Multisite 非対応などホスト側の代償が大きく、推奨は案 P | J4、§3.4 |

v0.2 の全文は git 履歴(コミット `8d0386a`)にある。

## 0. 要約

- **何を作るか**: `https://<名前>.dp.no32.tk/` に、ユーザごとの同人サークル紹介サイト(リンク集+マンガ作品の紹介)を出す(T.44。v0.5 までは `https://profile.xwp.jp/<名前>/`)。
  持ち主が lit.link のように自分で編集でき、見た目は WordPress のテーマそのもので変えられる。
  最初の目標は `https://takano32.github.io/f_tsf/` と同等の内容を `ftsf.dp.no32.tk` で出すこと。
- **設計原則は「標準優先」**: WordPress の標準の仕組みに乗る。標準から外れる要件は、独自実装で押し通すより要件のほうを曲げる。
- **構成**: WordPress Multisite(**サブドメイン型**)を、さくらのレンタルサーバに置く。プロフィール = ネットワーク内の 1 サイト。
  サイトの解決、サイトごとのテーマ選択、ユーザの共有とサイト単位の権限、アップロード容量の上限、サイトの公開停止や成人向けの目印、独自ドメインの割り当て — **どれもコア標準の機能**で、自作が要らない。
- **前段に Caddy を置く**(いまは GCP の e2-micro): サブドメインごとの証明書を自動で取り(on-demand TLS。ネットワークにあるサイトにだけ出す)、さくらへ中継する。
  さくらは登録済みのホスト名しか受け付けないので、Caddy は `doujin-profile.no32.tk` の名前でつなぎ、本当のホスト名と訪問者の IP を合言葉付きのヘッダで渡す。
  WordPress 側は `wp-config.php` の数行で受け取る。**標準から外れるのはここだけ**(§3.3)。
- **プラグインが作るのはコアに無いものだけ**: 同人向けの独自ブロック 4 種、新しいサイトの初期設定、招待コマンド、年齢確認、堅牢化。
- **残る課題**: 前段が米国にあるので、経路が日本 → 米国 → 日本になって遅い。さくらの国外 IP フィルタは前段の IP を許可して通した(T.25)が、前段経由では国外からのログインも通るので、2 段階認証が守りの本体になる(T.19)。本番の前段をどこに置くか(T.24)。
- **ホスティング規約は当面の判断材料にしない**(T.1.2。当面は公開しない)。

### 1.2 設計原則

1. **標準優先**: URL の解決、編集画面、見た目、認証、サイトの管理は、WordPress コアの標準機能で実現する。コアに無いものだけを作る。
2. **最小権限**: ネットワーク全体を触れる権限(特権管理者)は運営者だけ(`takano32` と `ftsf`。T.35)。運営者でない持ち主の権限は、自分のサイトの中に閉じる。
3. **リポジトリが正本**: サーバ上で直接編集しない。配備は rsync、検収は WP-CLI と curl(§12)。
4. **このサーバに置かなくても成立する**: 成人向けの画像は外部 URL でも扱える形にしておく(規約を判断材料にしない間も、ホストを移るときの保険として残す)。

### 1.3 スコープ

| 含む | 含まない(少なくとも当面) |
|---|---|
| ネットワークの構成と設定、サイトの初期設定 | 販売・決済・ダウンロード配信 |
| 同人向けの独自ブロック(プロフィールヘッダ、作品一覧、作品カード+サンプルビューア、リンクボタン)、年齢確認 | コメント・フォロー等の SNS 機能 |
| 持ち主の招待、公開前の確認、公開停止 | 公開のセルフ登録(§7.5。コア標準の機能はあるが開けない) |
| 運営者向けの WP-CLI(招待・投入・書き出し・診断) | 作品本編の配信(T.17 次第) |

- **裏側: さくらのレンタルサーバ**(ターゲット `sakura`)。FreeBSD 13.0、ログインシェルは csh。設置先は `~/www/doujin-profile/`(さくらでは `doujin-profile.no32.tk` に割り当て)。
  **WordPress 7.1.3・PHP 8.3.36・MySQL 8.0.40・WP-CLI 2.12.0**。サーバに node は無い(開発機には node 24 がある)。
- **Multisite(サブドメイン型。2026-10-24 に変換)**。ネットワークは `https://dp.no32.tk/`。いまのサイトはメインサイトだけで、中身はコアの初期データ。
- WordPress ユーザは `takano32`(特権管理者)と `ftsf`(2026-10-24 にサイト所有者が作成。特権管理者にする予定 = T.35)。§7.8。
- **同じアカウントに別のサイトが同居している**(`~/www/` 直下の静的サイト、`~/www/tsket/` の WordPress ほか)。DB は別。`~/www/doujin-profile/` の外には触れない。
- さくらの nginx が Apache の前にいる。`.htaccess` の書き換えは効く。HTML がキャッシュされるかは**未実測**。
- アップロードの上限は 5MB(CLI での値。Web 側は**未確認**)。ディスクは 300GB。
- **前段: GCP の e2-micro**(米国オレゴン、メモリ 952MB)の Caddy 2.6.2。`dp.no32.tk` と `*.dp.no32.tk` を受ける。同じ Caddy の後ろに別のサービスも同居している。
- DNS(value-domain): `dp.no32.tk` と `*.dp.no32.tk` は e2-micro を向く。`doujin-profile.no32.tk` はさくらへの CNAME。
- コアは自動更新される(同日中に 7.0.2 → 7.1.3 を観測)。コアの公開 API だけに依存し、更新で壊れにくく書く。
- 変換前のバックアップは `~/dumps/pre-multisite-20261024-1254/`。戻し方は [`caddy-front-trial.md`](caddy-front-trial.md) §4。
- **旧ホスト**(ターゲット `xserver`、Xserver for WordPress の `profile.xwp.jp`): 2026-09-18 の状態のまま(サブディレクトリ型の Multisite、`/` と `/ftsf/`)。扱いは T.26。

### 3.2 mu-plugin であることの制約

| 制約 | 対処 |
|---|---|
| `mu-plugins/` 直下の `*.php` しか自動ロードされない | ローダ `doujin-profile.php` → 本体 `doujin-profile/doujin-profile.php`(ts-library と同じ構成) |
| 有効化フックが発火しない | 初期化が要るものは「バージョン付きの冪等な初期化」で行い、WP-CLI からも呼べるようにする |
| rewrite rules を足すと flush の契機が無い | **足さない**。URL はコア標準(Multisite のサイト解決と固定ページ)に任せる |
| 管理画面から無効化できない・更新通知が無い | 意図どおり。配備は rsync(§12) |

**Multisite では mu-plugin はネットワーク内の全サイトで読み込まれる**。独自ブロックと初期設定を全サイトに行き渡らせるのに、ちょうどよい置き場所になる
(mu-plugins はもともと WordPress MU = Multisite の前身のための仕組み)。

### 3.3 前段とさくらの関係(実測 2026-10-24)

| さくら側の挙動 | 前段での手当て |
|---|---|
| 登録していないホスト名(`ftsf.dp.no32.tk` など)には 403 を返す | Caddy は `Host: doujin-profile.no32.tk`、SNI も同じ名前で、https でつなぐ |
| http で来ると https へ 302 | 上のとおり https でつなぐ。PHP には `HTTPS=on` で届く |
| 独自のヘッダは PHP まで届く。**`X-Forwarded-For` は届かない**(さくらが消す) | 本当のホスト名は `X-Doujin-Profile-Host`、訪問者の IP は `X-Doujin-Profile-Client-IP` で渡す |
| `REMOTE_ADDR` は直接つないだ相手(前段を通すと Caddy の IP) | 同上 |
| 国外からの `wp-login.php`・`wp-admin/` を 403 で拒む(国外 IP アドレスフィルタ) | フィルタは残し、前段(e2-micro)の IP アドレスを許可した(T.25)。前段の IP が変わったら許可も直す |
| ディレクトリの末尾スラッシュの転送(`/wp-admin` → `/wp-admin/`)を、さくら側の名前で返す | Caddy が `Location` の `https://doujin-profile.no32.tk` を元のホスト名に書き戻す |

WordPress 側の受け取り(`wp-config.php`、「編集が必要なのはここまでです」の直前。合言葉はサーバの上にだけ置く):

```php
if ( isset( $_SERVER['HTTP_X_DOUJIN_PROFILE_SECRET'], $_SERVER['HTTP_X_DOUJIN_PROFILE_HOST'] )
	&& hash_equals( DOUJIN_PROFILE_PROXY_SECRET, $_SERVER['HTTP_X_DOUJIN_PROFILE_SECRET'] )
	&& preg_match( '/^([a-z0-9-]+\.)?dp\.no32\.tk$/', $_SERVER['HTTP_X_DOUJIN_PROFILE_HOST'] ) ) {
	$_SERVER['HTTP_HOST'] = $_SERVER['HTTP_X_DOUJIN_PROFILE_HOST'];
	if ( ! empty( $_SERVER['HTTP_X_DOUJIN_PROFILE_CLIENT_IP'] ) ) {
		$_SERVER['REMOTE_ADDR'] = $_SERVER['HTTP_X_DOUJIN_PROFILE_CLIENT_IP'];
	}
}
```

プラグインではなく `wp-config.php` に置くのは、Multisite のサイト解決(`ms-settings.php`)がプラグインより先に走るため。合言葉が一致しない要求(さくらに直接来たもの)は、ヘッダを無視する。

## 4. 全体構成: サブドメイン型の Multisite + 前段 Caddy

### 4.1 Multisite で賄うもの(すべてコア標準)

`dp.no32.tk` がネットワーク、`https://dp.no32.tk/` がメインサイト、`https://<名前>.dp.no32.tk/` が各プロフィールのサイト。

| 要ること | 実現(すべてコア標準) |
|---|---|
| ユーザごとの URL(T.48) | Multisite(サブドメイン型)のサイト解決。サイトの中のページ(`/announce/`)もそのサイトの固定ページ |
| ユーザ管理と認証(T.49) | ユーザはネットワークで 1 つ(ユーザのテーブルを共有)、権限はサイト単位。ログイン・パスワードリセット・Cookie はコアのまま(Cookie はサブドメインごと) |
| 自分で編集(T.38) | 持ち主は自分のサイトの管理者。ブロックエディタとサイトエディタ |
| テーマの流用(T.39) | 運営者がネットワークで有効化したテーマの中から、**サイトごとに選べる**。スタイルバリエーション・パターン・フォントもテーマの標準機能のまま |
| 名前の規則(T.12) | コアの規則(§5.2) |
| アップロードの制限 | ネットワーク設定の「サイトのアップロード容量」「アップロードできるファイル形式」「最大ファイルサイズ」。アップロード先はサイトごとに別ディレクトリ(実測: `uploads/sites/<ID>/`) |
| プラグイン・テーマの導入やファイル編集の禁止 | 特権管理者にしかできない(コアの仕様)。`unfiltered_html` も特権管理者だけ |
| 公開停止 | サイトの状態「アーカイブ」「スパム」「停止」。WP-CLI にもある |
| 成人向けの目印 | サイトの状態「成人向け(mature)」 |
| 独自ドメイン(T.41) | サイトのアドレスをそのドメインに書き換える(4.5 以降の標準機能。前段の手当ては §11) |

### 4.2 通り道

```
訪問者 ──https──> Caddy(前段)                       ──https──> さくらの nginx ──> Apache + PHP(WordPress)
  Host: ftsf.dp.no32.tk   サイトごとの証明書(on-demand)     Host: doujin-profile.no32.tk
                          ask: ネットワークにあるサイトだけ   X-Doujin-Profile-Host / -Client-IP / -Secret
```

- URL のパスは変えずに渡す(`ftsf.dp.no32.tk/about/` → さくらの `/about/`)。どのサイトかはヘッダで伝える。
- 証明書は on-demand TLS(T.45)。発行してよいかは Caddy がさくらの WordPress に問い合わせて決める(`ask`)。サイトが無い名前は TLS の時点で断る(実測)。WordPress 側のコードは要らない。
- サイト名は証明書の公開ログ(Certificate Transparency)に載る。T.45 で了承済み。
- Caddy の設定・手順・戻し方は [`caddy-front-trial.md`](caddy-front-trial.md)。

### 4.3 サブドメイン型を選んだ理由

v0.5 まではサブディレクトリ型(`/<名前>/`)だった。サブドメイン型の難点(ワイルドカード DNS、サイトごとの証明書、ホストが登録済みの名前しか受けないこと)は、前段の Caddy で解けた。
比較の表は design-log(2026-10-24「Multisite の型」)。どちらもコア標準の型で、ブロック・テーマ・権限の設計(§6〜§9)は変わらない。

### 4.4 固定ページ案(固定ページ方式)

単一サイトのまま固定ページで作る案は、付録 C に控えとして残す(v0.4 でMultisite 案 を主軸にしたときの比較は付録 B)。

## 5. URL と名前

### 5.1 URL

| URL | 実体 |
|---|---|
| `https://dp.no32.tk/` | メインサイト。サービスの案内・規約・プライバシーポリシー(T.7) |
| `https://<名前>.dp.no32.tk/` | プロフィールのサイトのフロントページ |
| `https://<名前>.dp.no32.tk/<ページ>/` | そのサイトの固定ページ(例 `https://ftsf.dp.no32.tk/announce/`)。持ち主が自由に作れる |
| `https://<名前>.dp.no32.tk/wp-admin/` | そのサイトの管理画面。スラッシュ無しで開いても、Caddy が転送先を元のホスト名に書き戻す(実測) |
| ネットワークに無い名前 | 証明書が出ないので、TLS の時点で失敗する(実測) |
| `https://doujin-profile.no32.tk/` | さくら側の名前。直接開くと、ネットワークに無い名前として登録ページへ転送される(実測)。転送先は `NOBLOGREDIRECT` で変えられる(コア標準) |

### 5.2 名前の規則(T.12: コアの規則そのまま)

- **サイト名 = 持ち主のユーザ名**にする(招待コマンドが同じ文字列で両方を作る)。
- 規則はコアの検証関数(`wpmu_validate_user_signup()` / `wpmu_validate_blog_signup()`)に任せる: 英小文字と数字のみ、4 文字以上、数字だけは不可。
  禁止名もコアが持つ(`www` `web` `root` `admin` `main` `invite` `administrator`)。
  サブディレクトリ型だけに効く予約 10 語(`page` `blog` `wp-admin` など)と「メインサイトの固定ページと同じ名前の拒否」は、サブドメイン型では効かない。
  サブドメインは DNS のラベルなので 63 文字以内(コアが検査するかは未確認)。
- **コアは、既存ユーザと同名のサイト名を、そのユーザ本人のために確保する**(実測は旧ホストのサブディレクトリ型: 別のユーザとして `ftsf` を検査すると「このサイト名は予約済みです」。同じ検証関数なのでサブドメイン型でも同じはず)。
  「サイト名 = 持ち主のユーザ名」という設計と噛み合う。招待コマンドは、持ち主を渡して検査する。
- 運営用に取っておきたい語(`login` `about` `terms` `privacy` `contact` `help` など)は、**ネットワーク設定の「禁止名」に足す**(コア標準の設定欄)。
- `ftsf` は規則を満たす(英小文字 4 文字)。`f_tsf` は使えない(実測: コアの検査が「サイト名には半角英字の小文字 (a-z) と半角数字のみを含められます」と拒否。裁定 T.12 で了承済み)。
- **ユーザ名は公開情報になる**(名前 = ユーザ名 = URL)。WordPress コアの立場(「ユーザ名は秘密ではない」付録 A-6)と同じ。防御の本体は試行制限と 2 段階認証に置く(§10)。
- 名前の変更はネットワーク管理画面でサイトのドメインを書き換える(運営者だけ)。旧 URL からの転送は自動では付かない。証明書は新しい名前で初回アクセス時に取れる。

## 6. サイトの中身

### 6.1 新しいサイトの初期設定(プラグインが自動で行う)

コアは新しいサイトに「Hello world!」などの初期データを入れる。プロフィール用には合わないので、サイト作成時のフック(`wp_initialize_site`)で整える:

| 項目 | 設定 |
|---|---|
| フロントページ | 固定ページを 1 枚作り、スターターパターン(§6.3)を入れて「ホームページの表示」に設定する |
| 初期データ | サンプルの投稿・固定ページ・コメントを消す |
| コメント・ピンバック | 閉じる(ネットワーク全体で使わない。§10) |
| タイムゾーン・言語・パーマリンク | Asia/Tokyo、日本語、`/%postname%/` |
| サイトのタイトル | 招待時に渡したサークル名 |
| テーマ | ネットワークの既定(§9.1) |
| 公開前の状態 | 「準備中」(§7.6。T.11) |

### 6.2 独自ブロック(全サイトで使える)

| ブロック | 属性(主なもの) | 表示側の挙動 |
|---|---|---|
| プロフィールヘッダ | アイコン(メディア)、名称 (ja, en)、リード文 (ja, en)、ページ内ナビの有無 | ページ内のセクションからナビを自動生成 |
| 作品一覧 | 見出しの文言 (ja, en) | 子の作品カードを発売日時で 3 区分に振り分けて描画。予告が無ければ「新作予告」を出さない |
| 作品カード | タイトル・あらすじ (ja, en)、発売日時、発売日の表記(発売前・発売後、各 ja, en)、表紙(メディア / 外部 URL / FANZA ID)、販売リンク[](サービス種別・URL・sponsored・発売前の URL)、サンプル画像[](メディア / 外部 URL) | サンプルビューア(前後移動・矢印キー・Esc・枚数表示)。発売前後でリンクと表記を差し替え |
| リンクボタン | リンク[]: サービス種別(FANZA・DLsite・メロンブックス・とらのあな・BOOTH・pixiv・X・note・Circle.ms・Bluesky・Misskey・Fantia・FANBOX・Skeb・YouTube・その他)、URL、表示名 (ja, en)、sponsored | `rel` を自動で付ける(`noopener`、sponsored なら `sponsored`)。アフィリエイト表記の要否を判定 |

- どれも**サーバ側で描画する動的ブロック**にする(保存されるのは属性だけ)。表示の修正を、保存済みの全サイトに後から効かせられる。
- **見た目はテーマに委ねる**: 色・文字・余白はテーマのプリセット(CSS 変数)を参照し、ボタンはテーマのボタン要素のスタイルを継ぐ。独自ブロックにもコアの色・文字・余白の設定欄を付ける。
  持ち主がどのテーマを選んでも、独自ブロックがそのテーマの雰囲気に馴染むようにする(T.39 の要)。ネットワークで有効化するテーマごとに見え方を確認する。
- 表示側の JavaScript は、コア標準の Interactivity API を第一候補にする。
- エディタ用の JavaScript はビルドが要る。開発機(node 24)でビルドし、成果物をリポジトリに入れて配備する(サーバに node は無い)。

入力値の規則: URL は `https:` のみ。テキストはプレーンテキスト。件数に上限(作品 200、リンク 30、サンプル 80 枚/作品 など。値は実装時に確定)。
検証はサーバ側の描画時にも行う。`display_errors = On`(実測)なので、未定義キーや型のゆらぎで notice を出さないよう、値を正規化してから出力する。

## 7. 認証・権限

### 7.1 方針

1. **アカウントは WordPress のユーザ**(付録 A-1)。Multisite ではユーザはネットワーク全体で 1 つ、権限はサイトごと。独自の認証は作らない。
2. **特権管理者は運営者(`takano32` と `ftsf`)だけ**(T.35)。プラグイン・テーマの導入、ファイル編集、ネットワーク設定、サイトの作成と停止は特権管理者にしかできない(コアの仕様)。
3. **持ち主は、自分のサイトの管理者**(コア標準の、サイト単位の administrator)。独自ロールは作らない(§7.2)。
4. **登録は閉じる**(ネットワーク設定「登録を停止」)。アカウントとサイトは運営者が作る(招待制)。

### 7.2 持ち主にできること・できないこと(コア標準のサイト管理者)

| できる | できない(特権管理者だけ) |
|---|---|
| 自分のサイトの固定ページ・投稿・メディアの編集 | プラグイン・テーマのインストール、有効化、ファイル編集 |
| 有効化済みのテーマの中からの切り替え、サイトエディタ(テンプレート・スタイル・フォント) | `unfiltered_html`(スクリプトを含む HTML の保存) |
| サイトのタイトル・キャッチフレーズ・表示設定の変更 | 他人のサイトへのアクセス(明示的に追加されない限り) |
| 既存のネットワークユーザを自分のサイトに追加する(合同サークル向け) | 新しいユーザの作成(ネットワーク設定で許可しない) |
| 自分のサイトの削除(メール確認つき) | ネットワーク設定、サイトの作成・停止、アップロード容量の変更 |

単一サイトの administrator と違い、Multisite のサイト管理者は**ファイルにもコードにも触れない**。v0.3 までの「administrator を渡してはいけない」問題(`DISALLOW_FILE_EDIT` 未設定で任意コード実行と同義)は、Multisite 案 では構造的に解消する。

標準の権限をそのまま使う(原則 1)。絞るのは、標準の設定欄とごく小さなフィルタで足りるものだけ:

- プラグインのメニューはネットワーク設定で出さない(既定)。
- コメントとピンバックはネットワーク全体で閉じる(§10)。
- アップロードは画像だけ、サイトあたりの容量上限あり(ネットワーク設定)。
- サイトを削除されても名前は勝手に再利用されない(サイトを作れるのは運営者だけなので)。

### 7.3 ログイン後の導線(lit.link 風にする要)

- ログインしたら、**自分のサイトのフロントページのブロックエディタへ直行**させる(コアは既定で「主サイト」のダッシュボードへ送る。送り先を変えるだけ)。エディタは既定で全画面表示。
- 公開ページを見ている持ち主には「このページを編集」への導線が出る(コア標準のツールバー)。
- ダッシュボードはそのまま残す(テーマを替える、ページを足す、などをしたい人のため)。メニューを減らす「かんたん表示」は T.34 で検討。
- Application Passwords は持ち主には無効化する(権限の絞り込みができず、全権限を引き継ぐため。付録 A-8)。

### 7.4 招待の流れ

1. 運営者が `wp doujin invite <メール> --name=<名前> --title=<サークル名>` を実行する。
2. コマンドは、コアの検証関数で名前を検査し(§5.2)、ユーザを作り、サイト `<名前>.dp.no32.tk` を作ってその人を管理者にする(コアのサイト作成処理。§6.1 の初期設定が走る)。
   WP-CLI で作ったサイトは URL が `http://` で登録される(実測。CLI には https の文脈が無い)ので、作成直後に `home` / `siteurl` を `https://` にそろえる。証明書は初回アクセスで自動的に取れる。
3. コア標準の通知メールが、パスワード設定用のリンク(期限 24 時間のリセットキー)を送る(付録 A-7)。
4. 持ち主が内容を編集する。サイトは「準備中」で、運営者が確認して公開する(§7.6)。

### 7.5 公開のセルフ登録はしない

Multisite には、ユーザ登録とサイト作成をメール確認つきで受け付ける標準機能(`wp-signup.php`)がある。ただしオープン登録はスパムの実例が多く(付録 A-7)、
公開を考えるときの規約の論点(§3.4)にも近づく。ネットワーク設定で閉じたままにする。

### 7.6 公開前の確認(T.11)

新しいサイトは「準備中」で始める: サイトのメンバーと運営者以外には準備中の表示(503)を返す。運営者が内容を見て「公開」に切り替える。
コアのサイト状態(アーカイブ・停止)は持ち主自身も締め出してしまうので、ここだけは小さな独自実装になる。持ち主が載せた内容を公開前に見る歯止めとして入れる(規約を判断材料にしない間も、公開時の保険になる)。
公開後の編集は即時に反映される(事後の問題は §7.7 で止める)。

### 7.7 公開停止と退会(コア標準)

- 運営者は、サイトを「アーカイブ」または「スパム」にして即時に止められる(ネットワーク管理画面か WP-CLI の `wp site archive` / `wp site spam`)。訪問者には停止中の表示が出る。
- 成人向けの目印は `wp site mature`(または管理画面)で付ける。
- 退会は、サイトのアーカイブ+ユーザのサイトからの削除。名前は運営者が管理しているので、勝手に再取得されない。

### 7.8 既存アカウントの移行 👤

**`takano32` と `ftsf` は、どちらも運営者**(T.6 2026-09-18:「ftsf は管理者でもあります」)。さくらでもどちらも特権管理者にする(T.35 2026-10-24:「全権限わたしちゃおう」。同日の T.29.2「管理者権限あれば十分です」を改めた)。運営の画面は標準のネットワーク管理画面で、独自の運営パネルは作らない。`ftsf` は `ftsf.dp.no32.tk` の持ち主にもなる。

- 旧ホストでは、Multisite 化した時点で両方とも特権管理者になった(ネットワーク作成時点の administrator は全員が特権管理者になる。コアの仕様)。
- さくらでは、2026-10-24 にサイト所有者が `ftsf` を作った(メインサイトの administrator)。特権管理者にする作業は TASKS T.29.2。
- 訂正の記録: 2026-09-18 19:45 ごろ、Claude は `ftsf` を「持ち主にすぎない」と思い込んで特権管理者とメインサイトから外した。T.6 を受けて同日中に元へ戻した(design-log)。
- **今後招待する、運営者でない持ち主**は、最初からそのサイトの管理者だけにする(§7.4)。特権管理者にはしない。
- 特権管理者が 2 名いて、前段経由では国外 IP フィルタが実質効かない(§10.2)ので、2 段階認証(T.19)は運営者に必須とする。

## 8. 編集体験(lit.link のように)

lit.link の編集は「部品を足す・並べ替える・その場で書き換える・すぐ見た目が分かる」。WordPress でこれに当たる標準の道具がブロックエディタで、
ブロックテーマではエディタの中の見た目が公開ページとほぼ一致する。独自の編集画面を作らずに T.38 を満たす。

| lit.link に寄せる工夫 | 内容 |
|---|---|
| 直行 | ログインしたら自分のフロントページのエディタが開く(§7.3) |
| 雛形から始める | 新しいサイトはスターターパターン入りで作られる(§6.1) |
| 同人向けの部品 | 独自ブロック 4 種が挿入欄の先頭に並ぶ(独自のブロックカテゴリ) |
| 雰囲気を選ぶ | 外観 → テーマ、サイトエディタ → スタイル(どちらもコア標準の画面) |
| スマホ | ブロックエディタはスマホでも動くが、lit.link ほど軽快ではない。妥協点として明記しておく |

それでも足りない場合(スマホでの編集が主になる、など)は、T.34 で専用のフロントエンド編集画面を検討する(付録 A-9)。

### 運営者の道具(WP-CLI)

コア標準のコマンドで足りるものは作らない。

| やりたいこと | コマンド |
|---|---|
| 招待(ユーザとサイトの作成) | `wp doujin invite …`(§7.4。独自) |
| 内容の投入・書き出し | `wp doujin import <json> [--dry-run]` / `wp doujin export <名前>`(§6.4。独自) |
| 公開(準備中の解除) | `wp doujin publish <名前>`(§7.6。独自) |
| 一覧 | `wp site list`(コア標準) |
| 停止・成人向けの目印 | `wp site archive` / `spam` / `mature`(コア標準) |
| テーマの有効化 | `wp theme enable <テーマ> --network`(コア標準) |
| 診断 | `wp doujin doctor`(ネットワーク設定・堅牢化・初期設定の自己診断。読み取り専用。独自) |

## 9. 見た目: WordPress のテーマを流用する(T.39)

### 9.1 テーマはサイトごとに選ぶ

- 運営者が、使ってよいテーマを**ネットワークで有効化**する。持ち主は 外観 → テーマ で、その中から選ぶ。
- 対象はブロックテーマ(独自ブロックがテーマのプリセットに馴染む前提のため)。最初はサーバに入っている既定テーマ(Twenty Twenty-Five / Twenty Twenty-Four / Twenty Twenty-Three / Twenty Twenty-Two)で始め、
  wordpress.org のブロックテーマを運営者が選んで足していく。テーマの PHP はサイトの権限で動くので、**入れるのは運営者が確認したものだけ**。
- 新しいサイトの既定テーマは 1 つ決めておく(T.20)。

### 9.2 テーマの中での調整(コア標準)

| 機能 | 内容 |
|---|---|

### 9.3 f_tsf の見た目

### 9.5 年齢確認・時刻で変わる表示

- 年齢確認: サイトの状態が「成人向け(mature)」のサイトにだけ、全ページで出す。確認結果は localStorage(サブドメインごとに別になるので、**確認はサイトごと**)。「いいえ」で本文を消して離脱。ダイアログとしてのフォーカス管理を足す。

## 11. 独自ドメイン(T.41)

`ftsf.example.com` で `ftsf.dp.no32.tk` のサイトを見せる(ユーザ裁定 T.41)。f_tsf には元ドメイン `ftsf.me` があり(稼働中)、これをどう扱うかは T.8。

- **DNS**: そのドメインを前段の Caddy に向ける。
- **前段の Caddy**: いまは `dp.no32.tk` 系のブロックしか無い。独自ドメインも受けるには、任意のホスト名を on-demand TLS で受けるブロックを足す(`ask` がネットワークにあるサイトだけを許可するので、濫用は防げる)。

- ログインの Cookie はドメインごとになる(マップしたドメインでは、そのドメインでログインし直す)。
- 手順と制約が固まったら、運営者の作業手順書にする(T.34)。

## 付録 A. 参考にする既存プラグインとコアの仕組み

2026-09-18 に Web で調査した結果(公式ドキュメント・公式リポジトリを優先。調査は別エージェントが行い、出典を付けて報告したもの)。
番号は本文からの参照用。「推測」と書いたものは事実ではなく調査からの見立て。

### A-1. アカウントの置き場所 — ほぼ全員が `wp_users`

- BuddyPress・bbPress・Ultimate Member・WooCommerce・MemberPress はいずれも `wp_users` / `wp_usermeta` が唯一のアカウント基盤で、独自テーブルは `user_id` を持つ付属データ。
  bbPress は独自テーブルを作らない([bbPress](https://codex.bbpress.org/getting-started/before-installing/stored-database-data/))。
  MemberPress は「ユーザの作成・保存・管理・認証を完全に WordPress API に依存」と明記([MemberPress](https://memberpress.com/docs/where-is-data-stored/))。
- 独自のユーザテーブル+独自認証は少数派(Simple Membership、WP eMember)。しかも Simple Membership の公式文書自身が「会員レコードと WP ユーザレコードの 2 つを作って連携する」と述べており、
  結局は二重管理になっている([Simple Membership](https://simple-membership-plugin.com/understanding-the-connection-between-simple-membership-members-and-wordpress-users/))。
- 「アカウントを持たない人」を扱う定石は独自認証ではなく、`user_id` を空にできるデータ側の設計(WooCommerce、Easy Digital Downloads の customers テーブル)。
  → 本仕様の「プロフィールは投稿、持ち主は任意で紐付く」と同じ考え方。

### A-2. 低権限ロール

- WooCommerce の `customer` ロールの権限は `read` だけ([class-wc-install.php](https://github.com/woocommerce/woocommerce/blob/trunk/plugins/woocommerce/includes/class-wc-install.php))。
- 管理画面からの締め出しはロール名ではなく**権限で判定**: `edit_posts` / `manage_woocommerce` / `view_admin_dashboard` のどれも無ければ My Account へ転送。
  `admin-ajax.php` と `admin-post.php` は除外([class-wc-admin.php](https://github.com/woocommerce/woocommerce/blob/trunk/plugins/woocommerce/includes/admin/class-wc-admin.php))。いちばん真似しやすい形。
- Ultimate Member はロールごとに「wp-admin に入れるか」「管理バーを隠すか」を設定で持つ([UM](https://docs.ultimatemember.com/article/103-user-roles-settings))。
- bbPress の動的ロール: ロールを DB に保存せず実行時に `$wp_roles` へ足す。理由は「ロールや権限を変えるたびに DB 移行スクリプトが要るのは労力に見合わない」
  ([bbPress フォーラム](https://bbpress.org/forums/topic/roles-and-capabilities-in-bbpress-2-2/))。有効化フックの無い mu-plugin と相性がよい。

### A-3. 公開される人物像とアカウントの分離

- Co-Authors Plus: guest author は投稿タイプ `guest-author`。公開 slug は専用メタ、WP ユーザとの連携は `cap-linked_account`
  ([ソース](https://github.com/Automattic/Co-Authors-Plus/blob/master/php/class-coauthors-guest-authors.php))。
- PublishPress Authors: 著者の実体はタクソノミーのターム。WP ユーザとの対応は term meta で、無ければゲスト = アカウント不要
  ([ソース](https://github.com/publishpress/PublishPress-Authors/blob/development/src/core/Classes/Objects/Author.php))。
- コア: 著者 URL の slug は `user_nicename`(varchar 50)。`user_login` と別の値にできる。予約ユーザ名は `illegal_user_logins` フィルタ。
- BuddyPress のプロフィール URL は既定で `user_nicename`。Ultimate Member は 7 種類から選べる(ユーザ名・氏名・ID・ハッシュ・任意のメタ)。
- **Ultimate Member は、プロフィール URL から `/user/` を取り除いてルート直下にすることを公式に「不可能」としている**。理由はコアの予約語と経路の競合
  ([UM](https://docs.ultimatemember.com/article/1890-remove-the-word-user-or-profile-from-the-profile-url))。→ v0.2 の独自 URL 解決をやめた理由(付録 B)。

### A-4. 「自分の投稿だけ編集可」の標準手法

- `capability_type` が `post` / `page` 以外だと `map_meta_cap` は既定で false。**明示的に true にする**([WP_Post_Type::set_props](https://developer.wordpress.org/reference/classes/wp_post_type/set_props/))。
- 所有者限定は「`edit_others_*` / `delete_others_*` を与えない」ことで実現する。公開済みの自分の投稿の編集には `edit_published_*` が要る([map_meta_cap](https://developer.wordpress.org/reference/functions/map_meta_cap/))。
- `create_posts` は既定で `edit_posts` 相当に対応付けられる([get_post_type_capabilities](https://developer.wordpress.org/reference/functions/get_post_type_capabilities/))。→ 固定ページ案(付録 C)で新規作成の権限を分ける理由。
- メディア: コアは既定で絞り込まない。絞るなら `ajax_query_attachments_args`(モーダル)・`pre_get_posts`(一覧)・`rest_attachment_query`(REST)の 3 経路。
  ただし表示上のフィルタであってアクセス制御ではなく、`/wp-json/wp/v2/media` は未認証で全件一覧できる。→ §10.3。
- `unfiltered_html` を与えると KSES フィルタが丸ごと外れる = 保存型 XSS に直結。低権限ロールには付けない。

### A-5. mu-plugin の制約

- 「must-use プラグインでは有効化フックは実行されない」「サブディレクトリは探さない」([公式](https://developer.wordpress.org/advanced-administration/plugins/mu-plugins/))。
- `add_role()` はオプションに書き込む。毎回呼ばず条件付きで。**既存ロールへの再実行は権限リストの変更も含めて何もしない**([add_role](https://developer.wordpress.org/reference/functions/add_role/))。
- `flush_rewrite_rules()` は「性能面で極めて高コスト」([公式](https://developer.wordpress.org/reference/classes/wp_rewrite/flush_rules/))。→ rewrite rules を足さない(§3.2)根拠。
- 「バージョン付きの初期化」を明文で推奨する公式文書は見つかっていない(上の注意書きからの実務的な帰結 = 推測)。

### A-6. ユーザ列挙

- コアの公式見解: 「ユーザ名やユーザ ID は秘密と見なさない。REST の `/wp/v2/users` が公開で見えるのは意図したもの」
  ([Reporting Security Vulnerabilities](https://make.wordpress.org/core/handbook/testing/reporting-security-vulnerabilities/))。
- 経路は 4 つで条件が違う: `/?author=N`(公開投稿があるとき転送)、REST(`show_in_rest` な投稿タイプで公開投稿を持つユーザ。`public` かどうかは関係ない)、
  ユーザサイトマップ(`public` な投稿タイプで公開投稿を持つユーザ)、**oEmbed**(`author_name` と `author_url` を返す。見落とされやすい)。
- 未認証で返るのは `slug`(`user_nicename`)と `name`(`display_name`)だけ。`user_login` とメールは返らない。→ §10.2 の安価な緩和。
- 止め方: `rest_endpoints`、`wp_sitemaps_add_provider`([告知記事](https://make.wordpress.org/core/2020/07/22/new-xml-sitemaps-functionality-in-wordpress-5-5/))、`oembed_response_data`。

### A-7. 登録の流れ

- `wp_new_user_notification()` は平文パスワードを送らず、パスワード設定リンクを送る。鍵はハッシュして保存され、期限は既定 24 時間
  ([get_password_reset_key](https://developer.wordpress.org/reference/functions/get_password_reset_key/))。→ §7.4 の招待はこれに乗る。
- 招待制そのものはコアに無い。実質は「登録を閉じる+管理者が作る」。
- WordPress 7.0 で、一般設定の「新規ユーザのデフォルト権限」から Administrator と Editor が外された
  ([7.0 Field Guide](https://make.wordpress.org/core/2026/05/14/wordpress-7-0-field-guide/))。背景に、登録フォームの既定ロールを管理者にできてしまう権限昇格の実例がある。
- オープン登録のスパム被害は実例多数。BuddyPress は単一サイトでも `signups` テーブルでメール確認の 2 段階。

### A-8. コアの認証まわり

- WordPress 6.8 でパスワードは bcrypt に。リセット鍵や Application Passwords は BLAKE2b。既存ハッシュは次回ログイン時に自動で更新
  ([告知](https://make.wordpress.org/core/2025/02/17/wordpress-6-8-will-use-bcrypt-for-password-hashing/))。
- Application Passwords は REST / XML-RPC の Basic 認証専用で、**権限の絞り込みができず、そのユーザの全権限を引き継ぐ**
  ([統合ガイド](https://make.wordpress.org/core/2020/11/05/application-passwords-integration-guide/))。→ §7.3 で持ち主には無効化する理由。
- 2 段階認証は 2026-09 時点でもコアに無く、プラグイン([Two-Factor](https://wordpress.org/plugins/two-factor/))。
- nonce は認証・認可の代わりにならない。必ず `current_user_can()` と組み合わせる([Nonces](https://developer.wordpress.org/apis/security/nonces/))。

### A-9. フロントエンド編集か、管理画面か

- 会員系プラグインは**フロントで完結させるのが主流**(WooCommerce の My Account、MemberPress と Paid Memberships Pro の「会員をダッシュボードに入れない」設定、Ultimate Member)。
- 一方で「低権限ユーザに wp-admin を見せるべきでない」という WordPress 公式の推奨は見つかっていない。コアの既定はむしろ、`read` 権限でダッシュボードと自分のプロフィールに入れる。
- 公式が求めるのは場所を問わず nonce + 権限検査 + サニタイズ/エスケープの 3 点([Security](https://developer.wordpress.org/apis/security/))。
- 推測: フロント編集の利点は攻撃面の縮小と使い勝手、欠点は編集 UI を全部自作することによる不具合の増加。

### A-10. ルート直下 `/<slug>/` を投稿タイプに割り当てる

- `'rewrite' => ['slug' => '']` は効かない。コアが空の slug を投稿タイプ名で上書きする([class-wp-post-type.php](https://github.com/WordPress/wordpress-develop/blob/trunk/src/wp-includes/class-wp-post-type.php))。
- 投稿タイプの rewrite rule は固定ページに構造上負ける。同名の固定ページが実在すれば必ず固定ページが勝つ。
- **`wp_unique_post_slug()` は投稿タイプをまたいで重複を防がない**([リファレンス](https://developer.wordpress.org/reference/functions/wp_unique_post_slug/))。横断の一意性は自前で担保する。
- 定石は `request` フィルタで 404 を拾い直す方式。wordpress.org 配布の [`remove-cpt-base`](https://plugins.svn.wordpress.org/remove-cpt-base/trunk/remove-cpt-base.php) がこれで、解決順は 投稿 → 固定ページ → 対象 CPT。
  更新履歴は 404 関連の修正の繰り返し = 慢性的に壊れやすい領域。
- Multisite サブディレクトリ型の予約サイト名は 10 個(`page` `comments` `blog` `files` `feed` `wp-admin` `wp-content` `wp-includes` `wp-json` `embed`)。
  ユーザ名側の禁止語は `www` `web` `root` `admin` `main` `invite` `administrator`。サイト名に使える文字は §5.2 のとおり。ユーザテーブルはネットワーク全体で共有。

### A-11. 調査で確認できなかったこと

- core.trac.wordpress.org と wordpress.stackexchange.com は本文を取得できず、チケットや回答の中身は未確認。
- 2 段階認証のコア統合の計画。Xserver for WordPress における Multisite の公式サポート可否。

## 付録 C. 固定ページ案の要点 — Multisite 案が通らなかったときの控え

単一サイトのまま、プロフィールをトップレベルの固定ページにする案。全文は v0.3(コミット `dabbbce` の `docs/spec.md` §5〜§9)。

- **URL**: `/<名前>/` はコア標準の固定ページとして解決される(rewrite もフィルタも不要)。名前 = ユーザ名 = ページの slug。固定ページの slug は `_` を含められる。
- **権限**: 専用ロール `doujin_member`(`read` `edit_pages` `edit_published_pages` `upload_files`)。コア既定の author は固定ページの権限を持たず、editor は他人のページも編集できるため。
  固定ページの新規作成は別の権限に対応付けて運営者だけに与え(既定のままだと何枚でも作れる)、持ち主による slug・親・作成者・テンプレートの変更は保存時に無効化する。
- **見た目**: 有効なブロックテーマ 1 つが全プロフィールに効く。プロフィールごとの違いは、いちばん外のグループに当てるセクションスタイル(`register_block_style()` に theme.json 形式のスタイルを渡す。実測でコアが対応)とパターンで出す。
  サイト共通のヘッダ・フッタを出さない白紙のテンプレートをプラグインが登録する(`register_block_template()`。実測で利用可)。
- **絞り込み**: 持ち主が使えるブロックを限定する。メディアライブラリは自分のアップロードだけを見せる(一覧・モーダル・REST の 3 経路)。
  固定ページと添付ファイルは slug の名前空間を共有するので、持ち主のアップロードには接尾辞を付けて将来の名前の先取りを防ぐ。
- **ホストとの相性**: 単一サイトのままなので、CloudSecure・ステージング・バックアップがそのまま使える。
- **できないこと**: ユーザごとに別々のテーマ。独自ドメインは自前の実装(ホスト名とページの対応表)になる。
- 内容はどちらの案でも標準のブロックマークアップなので、独自ブロックと交換形式(§6)は共通。固定ページ案 で始めてMultisite 案 へ移すことも、その逆もできる。

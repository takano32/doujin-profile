# 設計ログ

doujin-profile の設計の**過程**を時系列で残す文書。

- 決まったこと・提案の**現在形**は [`spec.md`](spec.md)、導入先で**実測した事実**は [`environment.md`](environment.md)。
  ここには「いつ・何を調べ・何が分かり・どの選択肢を比べ・誰が何を決めたか」を書く。
- **追記のみ**。新しい記録を下に足す。過去の記録は書き換えず、誤りが見つかったら訂正の記録を足す。
- サイト所有者の判断は「**ユーザ裁定 YYYY-MM-DD**」と明記する(ts-novels と同じ流儀)。
- 区切りごとに git コミットする(ユーザ裁定 2026-09-18)。push はしない(リモート未設定)。
- 秘匿値(ログイン URL の変更値・DB 認証情報・メールアドレス)は書かない。

## 2026-09-18 キックオフ

Claude はプラグイン名から「自サークル 1 つの紹介 / 複数サークルの名鑑 / WP ユーザごとの拡張」を想定し、

### 3. サイト所有者が述べた目的

1. あるユーザ `f_tsf` について、`https://takano32.github.io/f_tsf/` の内容が `https://profile.xwp.jp/f_tsf/` で見られるような感じにしたい。
2. `hoge` ユーザなら `https://profile.xwp.jp/hoge/` でサイトを作りたい。

### 4. 調べたことと、分かったこと

#### 4.1 移植元 f_tsf(`/home/takano32/GitHub/f_tsf` のソースを読んだ)

- Astro 5 製、GitHub Pages 配信。ページは `index.html` と `announce.html`。canonical と OGP は元ドメイン `https://ftsf.me/` を指す。
- 成人向け同人サークルのリンク集: 最新作 / 新作予告 / これまでの作品 / 販売ページ(FANZA・DLsite・メロンブックス)/ アカウント(pixiv・X・note・Circle.ms)。
- 仕掛け: 日英 2 言語(ブラウザ言語で切替)、年齢確認ゲート(localStorage)、サンプル画像ビューア(連番を最大 80 枚まで探る。計 54 枚を同梱)、
  発売日時での自動切替(予告→最新作、DLsite の URL と rel の差し替え)、GA4、アフィリエイト表記。
- 表紙は DMM の CDN、店舗・SNS のロゴは各サービスの favicon をホットリンクしている。
- git 履歴にデザインの全面リスキンが複数回ある(最終的に元の紫×白へ戻している)。
- → 棚卸しと「doujin-profile での扱い」は spec §2。

#### 4.2 導入先(`ssh profile`、読み取り専用)→ 詳細は environment.md

- `ssh novels` と同じホスト(sv3.xwp.ne.jp)の別アカウント。Xserver for WordPress。
- WordPress 7.1.1・単一サイト・PHP 8.0.30・MariaDB 10.11.18・WP-CLI 2.8.1。node なし。コアはメジャー含め自動更新。
- `mu-plugins/` は未作成。有効プラグインは CloudSecure WP Security のみ。テーマは Twenty Twenty-Five。
- WordPress ユーザは `takano32` と `ftsf` で、**どちらも administrator**。ログイン名 `ftsf` と、公開したい slug `f_tsf` は一致しない。
- `DISALLOW_FILE_EDIT` 未設定 → administrator は管理画面から PHP を書き換えられる。
- `display_errors = On`。前段に nginx キャッシュ(消去はパネルのみ)。`uploads/` では PHP が実行されない。GD あり・imagick なし。

#### 4.3 公開面(外部から curl)

- `/f_tsf/` `/hoge/` は 404(ここを受け持つ)。`/sample-page/` は 200(ルート直下 1 セグメントは固定ページの名前空間)。
- ログイン URL は CloudSecure が変更済み(`/wp-login.php` は 404)。`/?author=N` も遮断されている。
- 一方で `/wp-json/wp/v2/users`・`/wp-sitemap-users-1.xml`・`/author/<ログイン名>/` は 200。**ログイン名は 3 経路で分かる**。XML-RPC も POST を受け付ける。
- → 持ち主のアカウントを作る前に塞ぐ(spec §10)。

#### 4.4 ホスティング規約(原文を取得して確認)

- [XServer for WordPress 利用規約](https://wp.xserver.ne.jp/rule/rule.php)の禁止事項に、(11) 猥褻な表現を含む情報の掲載、(13) 未成年者に有害な情報の掲載、
  (14) 裸体等の画像・動画の掲載、(22) 本サービスと同様のサービスの第三者への提供・再販売がある。
- エックスサーバー本体の [FAQ](https://www.xserver.ne.jp/support/faq/dont_contents_stint.php) は「同人系コンテンツの運用自体は禁止事項に該当しない」が
  「性行為、またはそれを連想させる画像・動画」は該当、ポルノサイト等へのリンクを含むものも禁止としている(別サービスの FAQ。こちらへの適用は未確認)。
- → f_tsf の成人向けサンプル画像をそのまま載せるのは危険。**設計より先に方針が要る**(spec §3.3、要決定 D1)。解釈を決めるのは Xserver。

#### 4.5 Multisite のサイト名規則(WordPress コアのソースで確認)

- ネットワーク管理画面のサイト追加は `^[a-zA-Z0-9-]+$`(`wp-admin/network/site-new.php`)。
- セルフ登録は英小文字と数字のみ・4 文字以上(`wpmu_validate_blog_signup`)。
- → **`f_tsf`(アンダースコア入り)は標準フローでは作れない**。予約語の一覧は slug 規則の下敷きにした。

#### 4.6 元ドメイン

- `https://ftsf.me/` は 200 で稼働中 → `/f_tsf/` の canonical をどちらに向けるかが論点になる(要決定 D8)。

### 5. 検討した選択肢と、現時点の推奨(すべて未裁定)

| 論点 | 比べたもの | 推奨と理由 |
|---|---|---|
| 全体構成 | A: 単一サイト+CPT+WP ユーザ統合 / B: Multisite サブディレクトリ型 / C: 単一サイト+独自ユーザ管理 | **A**。B は `f_tsf` が作れず、規約 (22) にも近づく。C は認証一式を自作することになり「一般的な設計」から最も遠い |
| アカウントとプロフィールの関係 | ユーザの属性として持つ / 別実体にして紐付ける | **別実体**(プロフィール = 投稿、持ち主 = 投稿の所有者)。slug とログイン名を切り離せる、複数プロフィール・持ち主交代・代理入力ができる |
| 持ち主の権限 | 既存ロールの流用 / 専用ロール | **専用ロール** `doujin_member`。administrator は任意コード実行と同義(4.2)なので渡さない |
| 登録 | セルフ登録 / 招待制 | **招待制**。セルフ登録はボット対策・承認・規約 (22) の確認まで含めて別途 |
| URL の解決 | rewrite rule を足す / `request` フィルタで解決 | **`request` フィルタ**。mu-plugin には有効化フックが無く flush の契機が無い。一致したときだけ介入するので固定ページに影響しない |
| コンテンツモデル | 1 プロフィール = 1 投稿に集約 / 作品を別 CPT | **MVP は集約**。権限検査が 1 点で済む。作品個別ページが要るようになったら分割 |
| 発売日時の切替 | サーバ側だけ / クライアント側でも | **両方**。前段キャッシュをこちらから消せないため |
| 進め方 | 一括 / 段階導入 | **段階導入**: Phase 1 は表示+運営者入力(ログインは管理者だけ)、Phase 2 で持ち主の編集 |

## 2026-09-18 先行事例の調査結果(認証・権限・URL)

キックオフの §7 で保留にしていた調査が終わった。詳細と出典は spec 付録 A。設計に効いた点だけ記す。

### 推奨を裏付けたもの

- **アカウントは `wp_users` に統合するのが規範**。BuddyPress・bbPress・Ultimate Member・WooCommerce・MemberPress のどれも独自のアカウント基盤を持たない。
  独自認証を持つ少数派(Simple Membership)も、結局 WP ユーザを併走させる二重管理になっている。→ 案 A の維持。
- **公開される人物像とアカウントを別実体にする**のは Co-Authors Plus と PublishPress Authors が実際にやっている形。→ 「プロフィール = 投稿、持ち主 = 所有者」の維持。
- bbPress の動的ロール(DB に書かないロール)は、有効化フックの無い mu-plugin と相性がよい。バージョン付き初期化と並ぶ選択肢として spec に記載。

### 設計を直した・足したもの

| 分かったこと | 反映 |
|---|---|
| `create_posts` は既定で `edit_*` に対応付けられる → そのままだと持ち主がプロフィールを何個でも新規作成でき、slug を占拠できる | §7.3: 新規作成を別権限に分け、運営者だけに与える |
| `capability_type` が独自だと `map_meta_cap` は既定 false(所有者判定が効かない) | §7.3: 明示を必須と記載 |
| `add_role()` は既存ロールに対して何もしない(権限の変更も反映されない) | §7.3: 差分を `add_cap()` / `remove_cap()` で適用 |
| アップロードした画像は実質公開(直接配信+未認証の `/wp/v2/media` 一覧)。メディアの絞り込みは表示上のフィルタにすぎない | §7.3: 「公開物として扱う」と明記。§10: 未認証の一覧を止める |
| 未認証の REST が返すのは `user_nicename` と `display_name` だけ | §10: 招待時にこの 2 つをログイン名と別値にする(コードほぼ不要の緩和) |
| oEmbed も著者情報を返す(見落とされやすい 4 つ目の経路) | §10 に追加 |
| コアは「ユーザ名は秘密ではない」という立場 | §10 の位置づけを「多層防御の一枚。本体はパスワード・試行制限・2 段階認証」に修正 |
| `'rewrite' => ['slug' => '']` は効かない。コアは投稿タイプ横断で slug の重複を防がない | §5.2・§5.3 |
| ルート直下の URL は**慢性的に壊れやすい領域**: 同方式の `remove-cpt-base` は 404 修正の繰り返し、Ultimate Member は公式に「不可能」としている | §5.3: いちばん壊れやすい箇所と明記。登録済み slug だけを拾う・予約語・横断一意性の 3 点で守り、実装前に検証する |

### 推奨が揺れたもの

- **持ち主の編集画面(D5)**: v0.1 は「絞り込んだ管理画面」を推していたが、調査では会員系プラグインの主流はフロントエンドで完結させる形だった。
  ただし WordPress 公式の推奨ではなく、UI を自作する分の不具合リスクと引き換え。
  → D5 の推奨を「編集のしやすさを製品の核にするならフロントエンド編集、早く確実に出すなら管理画面」と両論に改めた。決めるのはサイト所有者。

### 確認できなかったこと

- core.trac と WordPress Stack Exchange の本文(取得不可)。Xserver for WordPress の Multisite 公式サポート可否。

## 2026-09-18 見た目の切り替え(WordPress テーマの部品を流用できないか)

### 発端

サイト所有者: 「f_tsf とは違う雰囲気にすることもできたほうがいいので、ワードプレスのテーマからいい感じに部分を取り出して適用とかできないかな?」

### 調べたこと

- **サーバに入っているテーマ**(`ssh profile`、読み取り専用): 既定テーマ 4 つはどれもブロックテーマで GPL v2 or later。
  見た目が `theme.json` と `styles/*.json`(スタイルバリエーション)に機械可読な形で入っている。
  フルのバリエーションは計 28 個(TT5 8・TT4 7・TT3 10・TT2 3)。TT5 は配色プリセット 8 個とフォントの組 7 個も別に持つ。
  パレットの slug はテーマごとに違う(TT5: `base` / `contrast` / `accent-1…6`)。同梱フォントは欧文のみ。
- **TT5 のパターン**: 98 個。「Link in bio」のページ用パターンが 3 個あり、コアのブロック(段落・グループ・カラム・カバー・見出し・スペーサー)だけで組まれている。
- **WordPress 側の API**(存在確認のみ): `register_block_template()`、`wp_get_global_stylesheet()`、`WP_Theme_JSON_Resolver::get_style_variations()` が使える。
- **f_tsf の git 履歴**: 全面リスキン 4 回(PROOF SHEET / BOUDOIR NOIR / LACQUERED PLUM BOUDOIR / HOT-PINK PULP)は、どれも `global.css` と head のフォント指定だけの変更だった。
  CSS は各 1,000〜1,200 行、CSS 変数は 27〜47 個。Google Fonts の日本語書体(Murecho・Zen Old Mincho・Reggae One)を使っている。
  → 「構造は共通、見た目だけ差し替える」やり方は、この題材で既に 4 回うまくいっている。

### 比べたこと: テーマ流用の深さ 4 段階

| 段階 | 流用できるもの | 代償 |
|---|---|---|
| 1. トークン | 配色・フォントの組・余白・角丸・影 | レイアウトと装飾は流用できない |
| 2. ブロック描画 | テーマの造形とブロックパターンまで | 独立テンプレートからの転換。テーマはサイト全体で 1 つ。更新で見た目が変わりうる。独自ブロックの作り直し。攻撃面が広がる |
| 3. プロフィールごとにテーマ切替 | 任意のテーマ丸ごと | テーマはサイト全体を前提に作られている。検証の手間、更新への弱さ |
| 4. Multisite | サイトごとにテーマを選ぶ本来の形 | 案 B の代償すべて |

### 現時点の推奨(未裁定 → D14〜D16)

- **スキン方式**: トークン(CSS カスタムプロパティ)+同梱のスキン CSS の 2 層。持ち主による自由な CSS 入力は受け付けない。
- WordPress テーマからは**段階 1**で取り込む: WP-CLI で `theme.json` をスキン JSON に変換し、リポジトリに入れる。実行時にテーマへ依存しないので、コアの自動更新で見た目が変わらない。
- f_tsf の過去スキン 4 種は移植できる。
- 段階 2 の利点は「ブロックエディタがそのまま視覚的な編集画面になる」ことなので、見た目だけで決めず、編集画面の方針(D5)とセットで判断する。
  段階 1 のトークンを theme.json の構造に寄せておけば、あとから段階 2 へ進む道は残る。
- テーマから取り込むなら、このプラグインは GPL-2.0-or-later にする。
- 「スキン」という呼び名は、WordPress の「テーマ」(サイト全体に 1 つ)と混同しないための仮称。

J2〜J4 は、前の記録で「未確認」としていた 3 件。サイト所有者が通常のメッセージで「いずれも自分が入れた」と確認した。

### 裁定から読み取った原則: 標準優先

J4 の言い方(「標準から外れるようなら諦める」)は個別の名前の話にとどまらない。
**WordPress の標準の仕組みに乗り、外れる要件は独自実装で押し通さず要件のほうを曲げる**、を設計原則として spec §1.2 に置いた。
v0.2 までの設計(独立テンプレート、スキン、構造化メタ、`request` フィルタでの URL 解決)は、どれも「標準に無いので作る」側に寄っていた。

### 前提が変わって、比べ直したこと

1. **J3 → ページをブロックとして描画するのが前提になった**(v0.2 §9.6 の段階 2 以上)。独立テンプレートとスキンは廃止。
   見た目は有効なブロックテーマ+セクションスタイル(6.6 以降のコア標準。`register_block_style()` に theme.json 形式のスタイルを渡せることをサーバのコアで確認)+パターン+フォントライブラリ。
2. **J2 → 編集画面はブロックエディタ**。独自の編集 UI を作らずに「部品を足す・並べ替える・その場で書く・すぐ見た目が分かる」が手に入る。
   lit.link に寄せる工夫は、ログイン後の直行・ブロックの絞り込み・スターターパターン。スマホでの軽快さは妥協点。
3. **J4 → 固定ページなら `/<名前>/` がコア標準で解決できる**ことに気づいた。v0.2 はカスタム投稿タイプ+独自の URL 解決(調査で「慢性的に壊れやすい領域」と分かっていた)だったが、
   トップレベルの固定ページにすれば rewrite もフィルタも要らない。しかも固定ページの slug は `_` を含められるので、`f_tsf` も実は可能。
4. **J4 → Multisite の最大の障害(`_` が使えない)が消えた**ので、案 M として再評価した。

### 調べたこと(ホストの公式情報)

- **CloudSecure WP Security は Multisite 非対応**(公式の動作環境に明記)。Multisite にすると、いまログイン URL 変更や試行制限を担っているプラグインを外すことになる。
- XServer for WordPress の機能一覧に Multisite の記載は無い(可とも不可とも)。
- **ステージング環境**(各サイト 1 つ、本番と同期可)と自動バックアップ(14 日分)がある → 実験は安全にできる。
- 独自ドメイン: パネルで追加でき、無料 SSL も付く。追加時に自動で入るプライマリドメインへの 301 はパネルで変更できる。301 を外したときに同じ WordPress が応答するかは記載なし(未検証)。
- コア既定のロール: author は固定ページの権限を持たず、editor は他人のページも編集できる → 「自分の固定ページだけ」には専用ロールが要る(サーバで確認)。

### 現時点の推奨(未裁定 → D2)

**案 P(単一サイト。プロフィール = 固定ページ)**。R1〜R5 をコア標準だけで満たせ、ホストの道具立て(CloudSecure・ステージング・バックアップ)を失わない。
案 M(Multisite)が優れるのは「ユーザごとに別々のテーマ」と「コア標準の独自ドメイン」の 2 点で、これが必須要件になるなら案 M。
内容はどちらも標準のブロックマークアップなので、案 P で始めてあとから案 M へ移すことはできる。

### 設計上の代償として明記したこと

- **ユーザ名は公開情報になる**(名前 = ユーザ名 = URL)。v0.2 の「ログイン名を晒さない」方針は取り下げ、防御の本体を試行制限と 2 段階認証に置いた。コアの立場とも一致する。
- **持ち主が自分で編集できる = 運営者の知らないうちに規約違反の素材が載りうる**。初回公開の承認(D11)と公開停止コマンドが歯止め。
- コアの落とし穴: 固定ページと添付ファイルは slug の名前空間を共有する(メディアに `hoge.jpg` を直接上げると、あとで作る `/hoge/` が `hoge-2` になる)。持ち主のアップロードには接尾辞を付けて先取りを防ぐ。

### 保留・未確認(更新)

- ツール結果に混ざって届いた文章で、本人の通常のメッセージでまだ確認できていないもの(1 件):
  `ftsf.example.com` から `/ftsf/` の内容を閲覧できるようなドメイン設定はできるか。
  — もともと未決だった D8(`ftsf.me` と canonical)と地続きなので、構成比較の観点に入れ、spec §11 に「検討中」として整理した。要件として確定はしていない。
- 「マンガを編集」の範囲(作品カード+サンプル画像までか、本編を読ませるところまでか)→ D17。

### 次にやること

1. 👤 D1(成人向けコンテンツ)と D2(案 P か案 M か)の裁定。Xserver への問い合わせは D1 と Multisite の可否をまとめて。

3. 裁定が出たら独自ブロックの設計(属性と描画)を詳細化する。

## 2026-09-18 ユーザ裁定 J5: 案 M(Multisite)を主軸に(spec v0.4)

### 裁定の記録

| 日付 | 種別 | 内容 |
|---|---|---|
| 2026-09-18 | ユーザ裁定 J5 | 構成は案 M(Multisite)を主軸に検討する |

Claude の推奨は案 P(固定ページ)だった。サイト所有者は案 M を選んだ。案 M の弱点は WordPress の設計ではなく**このホストとの相性と規約**に集中しているので、
「検討して決める」ではなく「確かめて決める」に切り替えた: Xserver への問い合わせとステージングでの検証(Phase 0)が通れば確定、通らなければ案 P に戻る。

### 案 M を具体化して分かったこと

**コア標準で賄えるものが多く、自作が減る**(原則「標準優先」とよく合う):

| 要ること | コア標準の機能 | 確認方法 |
|---|---|---|
| 名前の規則 | ユーザ名・サイト名とも英小文字と数字、4 文字以上、数字だけは不可。予約語と禁止名もコアが持ち、ネットワーク設定で足せる | コアのソース(`wpmu_validate_user_signup` / `wpmu_validate_blog_signup`) |
| サイトの公開停止・成人向けの目印 | サイトの状態 public / archived / mature / spam / deleted | コアのソース(`ms-site.php`)。サーバの WP-CLI 2.8.1 に `wp site archive` `spam` `mature` などがあることも確認 |
| 新しいサイトの初期設定の差し込み口 | `wp_initialize_site` フック | 同上 |
| アップロードの制限 | ネットワーク設定の容量上限・ファイル形式・最大サイズ。アップロード先はサイト別 | コアの仕様 |
| 持ち主の権限 | サイト単位の administrator。プラグイン/テーマの導入・ファイル編集・`unfiltered_html` は特権管理者だけ | コアの仕様 |
| Multisite 化 | `wp core multisite-convert`(`wp-config.php` に定数を書く。`.htaccess` は手で差し替え) | サーバの WP-CLI のヘルプ。`wp-config.php` と `.htaccess` が書き込み可であることも確認 |

v0.3 で自作する予定だったもの(専用ロール、固定ページの権限の絞り込み、白紙テンプレート、セクションスタイルの登録、使えるブロックの制限、メディアライブラリの絞り込み、公開停止コマンド、成人向けフラグ)は、案 M では要らなくなる。
単一サイトで問題だった「administrator = 任意コード実行」も、Multisite のサイト管理者はファイルに触れないので構造的に解消する。

**ホスト側で新しく分かったこと**(公式マニュアル):

- XServer for WordPress のセキュリティは二本立て: **サーバ側の機能**(ログイン試行回数制限 = 24 時間ロック、国外 IP 制限。対象は `/wp-admin` `/wp-login.php` `/xmlrpc.php` `/wp-json` など)と、
  **パネルから制御される CloudSecure**(ログイン URL 変更・画像認証・ユーザー名漏えい防止・XML-RPC 無効化)。「セキュリティ自動最適化モード」が両方をまとめて適用する。
- Multisite にしてもサーバ側の機能は残る。ただし対象パスがルート基準なので、`/ftsf/wp-login.php` に効くかは未検証。自動最適化モードが、無効化した CloudSecure を戻さないかも未検証。
- ステージング環境はまだ作られていない(ホームディレクトリに見当たらない)。

**その他の実測**: f_tsf のサンプル画像は 54 枚で 19MB。本番サイトはほぼ空(初期データだけ)で、転換のコストはいまが最小。
最古の公開投稿が 1 か月以上前なので、管理画面のネットワーク設定からだとサブドメイン型を強制されるが、WP-CLI での変換ならサブディレクトリ型にできる見込み(未検証)。

### 残る独自実装

独自ブロック 4 種、新しいサイトの初期設定、招待コマンド、JSON とブロックの相互変換、「準備中 → 公開」の確認の仕組み(コアのサイト状態は持ち主も締め出すので、ここだけ自作)、年齢確認、head、堅牢化、TT5 の子テーマ(f_tsf の配色をスタイルバリエーションとして持つ)。

## 2026-09-18 Multisite 化の検証を実施(18:04〜18:10 JST)— 技術的には成立

手順・結果の全文は [`multisite-trial.md`](multisite-trial.md)。ここには判断に効いた点だけ記す。

### 結果

- 手順は書いたとおりに通った: バックアップ → CloudSecure 無効化 → `wp core multisite-convert` → `.htaccess` の WordPress ブロック差し替え → `/ftsf/` サイト作成。
- 確認項目 C1〜C7 はすべて通過。サイト別の URL も、サイト別パスの静的ファイルも、前段 nginx 経由で正しく解決された。`/` は TT5、`/ftsf/` は TT4 で表示される(**サイトごとに別のテーマ**が実際に動いた)。
- CloudSecure は、無効化すると自分で `.htaccess` のログイン URL 変更ブロックを消した。残骸なし。PHP の警告が画面に漏れることもなかった。
- **本番は Multisite のままにしてある。** ログイン URL は標準の `/wp-login.php` に戻った。

### 実測で覆った・確かまった前提

| 前提 | 実測 | 影響 |
|---|---|---|
| 「前段 nginx が HTML をキャッシュする」(ts-novels の環境文書からの類推) | **現在の設定ではキャッシュされない**。内容を書き換えると、キャッシュバスター無しの URL にも即時に反映(先に 6 回取得してからでも同じ)。静的ファイルだけが 7 日間キャッシュされる | 編集はすぐ公開ページに出る。発売時刻の切替はサーバ側だけでも正確になる(クライアント側の判定は保険として残す)。ts-novels 側の記述は別途見直す価値がある |
| 「管理画面からだと、古い投稿があるのでサブドメイン型を強制される」 | WP-CLI ならサブディレクトリ型で変換できた | 手順どおり |
| 「名前 = ユーザ名」はコアの規則と両立するか | コアは、既存ユーザと同名のサイト名を**本人のために確保**する(別人として検査すると「予約済み」) | 設計と噛み合う。招待コマンドは持ち主を渡して検査する |
| 特権管理者は `takano32` だけになる | **変換時点の administrator は全員が特権管理者になる**(コアの仕様)。`ftsf` も特権管理者 | 権限の強さは変換前と同じだが、原則には反している。D6 の重みが上がった |
| ネットワーク設定の既定値で足りるか | 登録停止・ユーザ追加不可・プラグインメニュー非表示は既定で望む状態。**アップロード容量の検査は無効**、許可形式は画像以外も含む | Phase 1 で直す設定として記録 |

### していないこと(正直な記録)

技術的な不安は消えた。残るのは **Xserver の回答**(Multisite の可否、第三者の招待、成人向けコンテンツ)だけ。否定的なら、文書化した手順で単一サイトに戻す。

## 2026-09-18 移転先ホスティングの調査(裁定 J9)

全文は [`hosting-research.md`](hosting-research.md)。友人と共有するための読みやすい版は、claude.ai のドキュメントとして別に作った(非公開。共有はサイト所有者がページの共有メニューから行う)。

### 結論

**mixhost か、カラフルボックスのアダルト対応サーバーの二択。** 名前の挙がったさくらインターネット(レンタルサーバ)と ConoHa は規約で不可だった。

| | mixhost | カラフルボックス(アダルト対応) |
|---|---|---|
| 成人向け | 「日本国内において合法なアダルトサイトの運営を行う事ができます」。専用プラン不要 | 専用サーバーで可。年齢認証が条件、アフィリエイト可、審査なし、「アダルトを理由に停止することはありません」 |
| 第三者の利用 | 規約第 17 条が ID・アカウントの発行を想定。人数上限なし | 規約第 5 条で可(第 14 条 1 項 23 号との関係は要確認) |
| Multisite | 公式に可。**複数ドメイン型も運用可能**と明記 | 公式手順あり |
| お試し | 30 日間返金保証 | 30 日間無料 |

第一候補を mixhost にした理由: このプロジェクトが要る 3 点(成人向け可・第三者へのアカウント発行・独自ドメインを割り当てる形の Multisite)を、すべて公式の文書で確認できた唯一のサービスだったから。

### 調べて分かったこと

- **さくら**: レンタルサーバは機能比較表で全プラン「アダルトサイト ×」。VPS とクラウドは約款に内容の規制が無く、「適用法令の下でわいせつ」「公序良俗」だけ(可とする明文も無い)。
- **ConoHa**: 会員規約第 21 条 (24)「性的な好奇心を煽る情報を掲載する行為」で、WING も VPS も不可。
- **GMO 系(ロリポップ・ヘテムル・コアサーバー・バリューサーバー・XREA・お名前.com)**: すべて明示的に不可。
- **シン・レンタルサーバー**: FAQ は「はい、可能です」。ただし (1) 第三者の利用は「計 5 ユーザーまで」、(2) 同じ規約ページの XServer アカウント規約に「猥褻な表現」「裸体」の禁止条項が残っていて FAQ と食い違う。
  後者は、いまの XServer for WordPress で問題にした条文と同じもの。つまり**この条文があること自体は「成人向け不可」の決め手ではなく、サービスごとの運用(FAQ)が実際の線引きを決めている**。
  XServer for WordPress の運用がどちらなのかは、問い合わせないと分からない。
- **比較サイトの「アダルト可」一覧は当てにならない**: サービス終了済みの FUTOKA、同人(二次創作)可を成人向け可と読み違えたと思われるラッコサーバー、公式に裏が取れない JETBOY。
- **海外を選ぶ理由はほぼ無い**: マネージド WordPress(Kinsta・Pressable・SiteGround・WordPress.com)は明示的に不可。明示的に可の Hostinger は日本に拠点が無い。
- **新しい論点**: カラフルボックスの規約が、第三者にサービスを提供する場合の電気通信事業法の届出に触れている。招待制の紹介ページが該当するかは、どのホストでも確認が要る。

### 進め方の記録

- 調査は 3 系統の並行(さくら・ConoHa・GMO 系 / 成人向け可の国内共用 / VPS と海外)。公式ページだけを根拠にした。
- 推奨の決め手になる文言(mixhost の成人向け・第 17 条・複数ドメイン型 Multisite、カラフルボックスの条件と第 5・14 条、シンの FAQ・再販条件・規約、さくらの比較表と注意事項、ConoHa の第 21 条と FAQ)は、Claude が原文を取り直して確認した。
  それ以外(料金や仕様、海外各社など)は調査エージェントの報告による。Hostinger だけはアクセス制限で再確認できなかった。内訳は hosting-research.md §7。

### 次にやること

## 2026-09-18 訂正: `ftsf` は運営者でもある(ユーザ裁定 J12)

| 日付 | 種別 | 内容 |
|---|---|---|
| 2026-09-18 | ユーザ裁定 J12 | 「ftsf は管理者でもあります」— 運営者は `takano32` と `ftsf` の 2 名 |

### 何が起きたか

終業前の手当てで、Claude は `ftsf` を特権管理者とメインサイトから外し、`/ftsf/` のサイト管理者だけにした。
`ftsf` を「最初の利用者(持ち主)」としか見ておらず、運営側でもあるという前提を欠いていた。サイト所有者の指摘を受け、同日中に元へ戻した。

| | 状態 |
|---|---|
| 変更前(Multisite 化の直後) | `takano32`・`ftsf` とも特権管理者、両サイトの administrator |
| 誤った変更(19:45 ごろ) | `ftsf` を特権管理者から外し、メインサイトの所属も解除 |
| 復旧後(いま) | 変更前と同じ。`wp super-admin add ftsf` と、メインサイトでの `wp user set-role ftsf administrator` で戻した |

堅牢化用の mu-plugin(XML-RPC の停止など)は、この件とは無関係で、そのまま有効。

### 教訓

- **人のアカウントの権限を変える操作は、「やりたいことをやって」のような包括的な了承では行わない。** 対象と内容を名指しした了承を取る。
  今回は Claude が「外してよければ言ってください」と提案した直後に包括的な了承を受け、それを個別の了承と読んだ。戻すのは 1 コマンドで済んだが、前提(その人が何者か)を確かめていなかったのが根本の誤り。
- spec が「特権管理者は運営者だけ」と書きながら、**運営者が誰かを確かめていなかった**。D6 を「`ftsf` を外すか」という問いにした時点で、前提の確認が抜けていた。

### 反映

- spec v0.5.4: 運営者は `takano32` と `ftsf` の 2 名(§1.2・§1.4・§3.1・§7.1・§7.8)。今後招待する「運営者でない持ち主」は、そのサイトの管理者だけにする、という設計は変わらない。
- 特権管理者が 2 名いるので、2 段階認証(D19)の重みが上がった。
- Xserver への問い合わせ文案の「プラグイン・テーマの導入は私だけが行う」を、事実に合わせて「運営者(私と、共同で運営する 1 名)だけ」に直した。

### サブディレクトリ型とサブドメイン型(Claude の推奨: サブディレクトリ型)

| 観点 | サブディレクトリ型 `/<名前>/` | サブドメイン型 `<名前>.doujin-profile.no32.tk` |
|---|---|---|
| 要件 R1(`/<名前>/` でユーザごとのサイト) | そのまま満たす | R1 を書き換えることになる |
| ホストへの要求 | `.htaccess` の書き換えだけ。さくら・Xserver の両方で動くのを確認済み | ワイルドカード DNS(value-domain で設定できる)に加えて、さくら側でワイルドカードのサブドメインを受けられるかの確認が要る(公式の記述は未確認)。Xserver の `profile.xwp.jp` はそれ自体がサブドメインなので、そもそも組めない |
| HTTPS | 証明書 1 枚で全サイト | サイトごとに証明書を発行する(ワイルドカード証明書は DNS 認証になり、さくらの無料 SSL では難しい見込み) |
| サイトを足す手間 | `wp site create` だけ | そのたびにコントロールパネルでのドメイン追加と証明書の発行が要る見込み |
| 「どこでも使える」(同日の裁定) | ホストを選ばない | ホストの DNS・SSL 機能に依存する |
| サイト同士の分離 | 同じオリジン。ただしサイト管理者には `unfiltered_html` が無い(コア標準)ので、他のサイトにスクリプトを仕込む経路は無い | オリジンが分かれる |
| 見た目の独立性 | URL がネットワークの下に見える | それぞれ独立したサイトに見える |
| 後から変える | 型を後から変えるのは重い(本文中の URL・設定の書き換え)。独自ドメインの割り当てはどちらの型でもコア標準でできる | 同左 |

推奨の根拠: 要件 R1 と、同日の「どこでも使えるように」の裁定にそのまま合う。サブドメイン型の利点(見た目の独立)は、必要になったサイトにだけ独自ドメインを割り当てれば得られる(コア標準)。

## 2026-10-24 ワイルドカード証明書でサービスできるかの調査

| 日付 | 種別 | 内容 |
|---|---|---|
| 2026-10-24 | 依頼 | 「ねんのためだけど、ワイルドカード証明書でサービスできないかも調べてね」 |

Let's Encrypt でワイルドカード証明書(`*.dp.no32.tk`)を取るには **DNS 認証(DNS-01)が必須**。`_acme-challenge.dp.no32.tk` の TXT レコードを、発行・更新(約 60 日ごと)のたびに自動で書き換えられる必要がある。

### 調べたこと(2026-10-24)

| 道具 | value-domain への対応 |
|---|---|
| Caddy の DNS プラグイン(`caddy-dns/*`、`libdns`) | 無い |
| acme.sh の `dnsapi/` | 無い(`dns_v*` は variomedia・veesp・vercel・virakcloud・volcengine・vscale・vultr) |
| lego の `providers/dns/`(231 個) | 無い |
| certbot | 有志のプラグインがある(`chrono-meter/certbot-dns-valuedomain` ほか。公式ではない) |
| value-domain の API | ある(`https://api.value-domain.com/v1/`、Bearer 認証)。DNS は「設定の取得」「設定の変更(PUT)」で、レコード 1 件の追加ではなく設定全体の置き換えに見える(要確認)。自動化で他のレコードを壊すおそれがある |

### 成り立つ案

1. **CNAME での委任(推奨)**: value-domain に `_acme-challenge.dp.no32.tk` → API で書ける別のゾーン、の CNAME を 1 行だけ置く。別のゾーンは Google Cloud DNS(GCP は既にある。Caddy のプラグインは `caddy-dns/googleclouddns`)か、自前の acme-dns(`caddy-dns/acmedns`)。Caddy は `dns_challenge_override_domain` で委任先に TXT を書く。
   - Caddy はプラグイン入りのビルドに入れ替える(Ubuntu の 2.6.2 にはプラグインが無い。最新は 2.11.7)。
2. certbot + 有志のプラグインで取り、Caddy にはファイルで読ませる。更新後に Caddy を reload するフックが要る。value-domain の資格情報を前段のマシンに置き、設定全体を置き換える API を使う点が弱い。
3. value-domain 用の libdns モジュールを自作する。標準優先から外れる。

### on-demand TLS(サイトごとの証明書)との比較

| 観点 | ワイルドカード | on-demand(サイトごと) |
|---|---|---|
| **名前が公開されるか** | `*.dp.no32.tk` だけが Certificate Transparency のログに載る | **サイトを作るたびに `<名前>.dp.no32.tk` が CT ログに載り、誰でも検索できる**。当面非公開という前提と相性が悪い |
| 濫用・レート制限 | 1 枚なので心配が無い。`ask` も要らない | 任意の名前で発行を起こされうるので `ask` が要る |
| 初回アクセス | すぐ | 発行の数秒を待つ |
| 用意するもの | CNAME 1 行、委任先のゾーンと資格情報、プラグイン入りの Caddy | 何も要らない(いまの Caddy のまま) |
| 本番(国内の Caddy)への移し替え | 委任先と資格情報を持っていくだけ | 何も要らない |

Claude の推奨: **当面非公開なら、CNAME 委任でのワイルドカード証明書**。サイト名を CT ログに出さずに済むのが決め手。委任先は、GCP の上にある Google Cloud DNS が手軽。

- 追記(同日): 「ファイルで認証することもできないか」との問いに対して。**ファイルを置く認証(HTTP-01)ではワイルドカード証明書は取れない**。Let's Encrypt はワイルドカードに DNS-01 を必須としていて、CA/Browser Forum の基準でも、ファイルを置く方法はワイルドカードには使えない。有料の CA でも、ワイルドカードの認証は DNS かメールになる。ファイル認証で取れるのは名前ごとの証明書(= on-demand と同じで、名前が CT ログに載る)。

## 2026-10-24 コメントと XML-RPC の守りを配布物のプラグインにする(ユーザ裁定。選択式)

| 日付 | 種別 | 内容 |
|---|---|---|
| 2026-10-24 | ユーザ質問 | 「プラグインでできないんか？」「普通に配布されてるやつね」 |
| 2026-10-24 | ユーザ裁定 | 「配布物を 2 つ入れる」(推奨は Disable Comments だけだった) |

- wordpress.org の **Disable Comments**(100 万以上で有効。ネットワーク有効化で全サイトに一括で効く。ピンバックと `X-Pingback` も止める)と **Disable XML-RPC**(20 万以上。`xmlrpc_enabled` を false にするだけ。Multisite で効かないというレビューあり → 入れたあと確かめる)。

手順(実行前に記す):
1. `~/dumps/pre-doujin-profile-comments-xmlrpc-20261024/` に `wp db export`。
2. `wp plugin install disable-comments disable-xml-rpc` → `wp plugin activate --network` の両方。
3. Disable Comments の設定をネットワーク全体・すべての投稿タイプで「止める」にする。
4. 確かめる: `ftsf.dp.no32.tk` の「Hello world」でコメント欄が出ないこと、`X-Pingback` が出ないこと、`xmlrpc.php` の認証の要るメソッドが「無効」で返ること。ログインと表示が壊れていないこと。
